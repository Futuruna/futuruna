# Futuruna Compatibility Guide: 0.2.x

This guide records the changes delivered with 0.2.0 relative to 0.1.1.
The [compatibility policy](../compatibility-policy.md) defines the categories;
[feature stages](../feature-stages.md) remain the authority for maturity.

## Stable Surface Changes

No stable surface is promoted or intentionally removed by this release.
Package metadata, CLI version output, citation metadata, and website version
labels advance together to 0.2.0.

### Post-release assertion messages

`assert_with_message(Bool, String) -> ()` is an additive runtime builtin.
Its two arguments are evaluated eagerly in both interpreted and native code.
False stops ordinary execution or becomes a case-local `runa call` diagnostic;
the supplied message is preserved as text, not interpreted as a format string.
Existing one-argument `assert` is unchanged. This does not add proof authority
or make partial rules total. Programs using the new builtin need a compiler
built after this addition; the original 0.2.0 release does not provide it.
Shadowable registry builtins now also respect lexically typed callable values,
not only named function declarations; native code previously could emit the
builtin instead of the local closure. The assertion regression covers both.
Native builtin templates substitute only their original placeholders: text
such as `{1}` inside an argument is no longer reinterpreted as another
substitution, which could previously corrupt the generated Rust.

## Deprecations

None introduced by this release.

## Bug-Fix Exceptions

- Ordinary `match` expressions now compile string-literal patterns through
  value comparisons instead of emitting invalid Rust expressions as patterns.
  This includes text nested in constructor fields and tail-recursive matches.
  Literal matching precedes user guards, the subject is evaluated once, and
  fallback bindings keep their existing ownership behavior. This repairs the
  stable native behavior contract; no source migration is required. Regression
  coverage includes escaped/Unicode text and generated-name collision cases.

- Inline modules expose their locally declared rule families as callable
  members, matching native execution and qualified imports. The interpreter
  previously omitted registry-only rules from module bindings, producing unit
  instead of a value; a surrounding collection operation could hide that as a
  successful zero. Member calls retain the declaring namespace and do not
  expose parent-only rules. Calculations additionally reject non-callable
  callee values instead of suppressing the runtime error. This is a behavioral
  wrong-result fix, with calculation and interpreted/native regression coverage.

- The shared frontend rejects known `List + List` operands. `+` has never
  implemented list concatenation: native code rejected it, while the interpreter
  could yield unit and a surrounding `length` could silently report zero.
  Use `concat(left, right)` instead. Calculation invocation also rejects
  unsupported arithmetic operands at runtime, including indirect expressions
  whose operand types are not statically resolved. Numeric addition and string
  concatenation are unchanged. This is a source/behavioral bug-fix exception,
  covered at the frontend, calculation, diagnostic and differential boundaries.
- Structural map/set keys retain lexical display-key iteration order across
  interpreter and native execution. Lookup and equality still use structural
  identity; distinct keys that print alike are not collapsed by iteration.
- Ordinary generated Boolean rule calls can establish that their own typed
  head matches, including captured and nullary predicates. A matched false
  clause returns `False`; this does not issue a context-independent miss
  certificate or expand solver/Explore proof authority. Genuine unproven
  misses and partial value families continue to fail closed.
- Backend result typing now includes rule-derived global bindings, string
  concatenation, and exported primitive returns from qualified sources by
  alias and arity. Imported nominal ownership is not erased. Builtin/prelude
  generic constructor signatures are deduplicated by their full field schema.
  Nullary constructors do not acquire distinct identities from a field-layout
  flag. Global bindings and rule results share a bounded inference fixed point;
  forward RuleScope dependencies work without certifying unanchored cycles.
  Nested constructor patterns no longer certify exhaustive coverage merely
  because their outer constructors cover the type's variants.
- Generic constructor-pattern payloads retain their instantiated parent types
  in native code, including named fields and same-spelled constructors owned
  by different types. Builtin `not` retains its Boolean backend result without
  overriding an authored binding or granting a new proof certificate.
- SMT rule-call validation uses the same default `Int` sort for unbound
  invariant variables as the emitted declarations. Existing program bindings
  and nominal constructors are not defaulted. Arithmetic backend typing does
  not prove unbounded integer arithmetic total: verification can report an
  unsupported proof even when a particular concrete call executes correctly.
  Namespace verification fixtures use globally total rules; separate negative
  regressions retain the arithmetic, partial, recursive and higher-order limits.
- Guarded value-rule families need an explicit unconditional fallback when
  the native dispatcher cannot establish exhaustive coverage. Complementary
  user-written guards alone are not a totality certificate. Export graph
  snapshots now include the public constructors exported with their ADT.
- Checked bare constructor resolution now rejects mixed nullary/non-nullary
  spellings even with an expected result type. Runtime value lookup cannot
  select an arity, so treating that ambiguity as an exact nullary value was
  unsound. Give the constructors distinct names. Compiler regression coverage
  keeps both unannotated and annotated uses outside exact proof authority.
- Integer collection `sum` retains its ordinary generated return type inside
  rules and RuleScopes without adding a new exact-proof intrinsic. A plain
  import already flattened at the root also retains its shared nominal owner
  when reached through a qualified module. These repair integration regressions
  caught by the existing newline-layout, import-mesh, and downstream canaries.
  Root/qualified source-order parity and integer-sum regressions are permanent
  unit and differential coverage; the broader cross-parent ownership work
  without a root owner remains tracked separately in `td-625bb9`.
  Interpreter constructor patterns, typed rule heads, equality, and collection
  keys now use plain/hash-import declaration provenance consistently. Separate
  qualified aliases and identical-looking declarations from different sources
  remain distinct; cached collection keys do not depend on root import order.
- Rule dispatch and checked Boolean misses are aligned across the checked
  interpreter, generated Rust, and supported solver lowering. This is a
  behavioral and verification bug-fix exception: an unsound proof or an
  interpreter-only empty-string result for a checked Boolean family is not
  supported behavior. The context-closed boundary and embedder migration are
  described in the [Boolean rule-miss entry](0.1.x.md#2026-08-19-boolean-rule-misses),
  which was recorded during development and ships in this integration.
  Context-sensitive families outside the proven subset retain their documented
  limits. Regression coverage includes `tests/verify_cli.rs`, the
  `tests/fixtures/verify/rule_dispatch_*` fixtures, and compiler unit tests.
- Qualified callable verification preserves module identity, exported/private
  boundaries, and rule-family arity instead of conflating same-named callables.
  Category: verification compatibility; an unsound result may now fail closed.
  Call only exported members through qualified imports. Permanent coverage is
  in the `qualified_namespace_*` verification fixtures and `tests/verify_cli.rs`.

## Preview And Experimental Notes

- Boligjob now checks a private supplier's age at the end of the work year,
  not the selected deduction year. A delayed payment previously could grant a
  service deduction for work by someone who turned 18 only in the later year.
  Known under-age suppliers remain valid facts with no entitlement; unknown or
  impossible supplier facts remain invalid. Claimant age, company suppliers,
  annual caps and payment-year routing are unchanged. Shared supplier metadata
  adds explicit source-backed questions for both compact and canonical inputs,
  including spouses. Regenerate templates for the changed Preview fingerprint
  and recalculate affected results without altering source dates. See the
  [invoice guide](../../examples/danish-income-tax/boligjob.md#private-udførere-arbejdsår-er-ikke-altid-fradragsår).

- LL §9(1) depreciation work-use shares outside 0–10000 basis points now
  invalidate the employee-expense facts and withhold canonical comparison,
  including an active spouse. Previously these impossible shares were accepted
  as valid zero deductions. Zero remains valid but ineligible; other ordinary
  eligibility decisions and valid-share arithmetic are unchanged. A named
  control checks source facts before coordination as well as the resulting
  expenses. Input help distinguishes work-use share from depreciation rate,
  pre-allocation depreciation from purchase price, and raw expenses from the
  already-net report box 58. No input types change; metadata changes the Preview
  fingerprint. Regenerate templates and review facts rather than editing hashes
  or clamping invalid percentages. See the
  [input guide](../../examples/danish-income-tax/personskat-validity.md#øvrige-lønmodtagerudgifter).

- Canonical wage input help now has one type-anchored definition shared by the
  taxpayer and spouse. Both explicitly distinguish wages from employer pension,
  ATP, net payments, aggregate personal income and separately entered components;
  both carry the same official input guidance. The old spouse wording omitted
  those boundaries. Input paths, types and tax formulas are unchanged, but labels,
  questions, help and sources change the Preview contract fingerprint. Regenerate
  templates and transfer reviewed facts rather than changing the stored hash.
  See the [wage input guide](../../examples/danish-income-tax/pension-og-fradrag.md#løn-og-arbejdsgiverpension-brug-ikke-samme-beløb-to-gange).

- LL § 9 C ferry/flight expenses now lose the unused portion of the daily
  24-km threshold; previously the whole documented expense was deducted even
  with fewer than 24 land kilometres. The floor is zero, and the ordinary
  annual rate is used; zero travel days give no ticket deduction.
  Land-distance and bridge deductions are unchanged.
  The corrected amount also feeds the canonical annual low-income supplement
  and spouse calculation. Additive result fields expose the residual threshold,
  ticket deduction in øre and sources; projected input help explains travel
  days, land-only distance and full ticket costs. Regenerate templates because
  metadata/output changes alter the Preview contract fingerprint; preserve
  actual ticket costs, not amounts fitted to the old result. See the
  [guide and interpretation boundary](../../examples/danish-income-tax/personskat-faerge-og-fly.md).

- The personal-allowance model now expresses its two age-status alternatives
  and the two loss-credit rate branches with exhaustive `match`/`if` bodies.
  This removes native scalar-dispatch rejections in the §§10–13 import without
  changing tax amounts, historical exceptions, source quotations or input
  fields. Missing annual parameters still fail rather than becoming zero;
  historical 2010-base amounts are not extended annual-rate coverage. Focused
  native/interpreter and spouse-transfer regressions live in
  `tests/personfradrag_domain_test.runa` and `tests/tax_parameter_domain.rs`.
  This is a model-source compatibility repair, not a relaxation of compiler
  totality checks or a claim that the full Personskat graph compiles natively.

- Canonical Personskat now withholds comparison if a child-maintenance recipient
  has a different birth date from the person whose tax is being assessed. This
  fixes accepted parent/child input contradictions; it does not authenticate
  identity or alter the maintenance formulas. Parent-payer and adult-alimony
  routes remain distinct. No new input fields are added, but revised role help
  changes the Preview schema fingerprint: regenerate templates, review the
  actual recipient and rerun affected cases. See the
  [maintenance guide](../../examples/danish-income-tax/personskat-underholdsbidrag.md)
  and permanent `tests/personskat_maintenance_recipient*` checks.

- Personskat recurring gifts now cap all payments under one identified LL §12
  agreement together before the shared annual income ceiling. This corrects
  split-payment over-deductions, not language semantics. The Preview source and
  input contract add required `aftale_identifikation` and
  `ordinært_betalingsforløb_bekræftet` fields to `Ll12BindendeLøbendeYdelse`;
  positional constructors/patterns gain those two leading fields. Regenerate
  fingerprinted templates and review the facts; no automatic agreement-ID or
  scope-confirmation migration is sound. The annual output adds `par12_aftaler`
  and `par12_aftaler_gyldige`; provisional per-payment §12 amounts must not be
  summed as an annual deduction. Inconsistent or unsupported facts now withhold
  the canonical comparison. See the [gift guide](../../examples/danish-income-tax/personskat-gaver.md)
  and permanent `tests/personskat_recurring_gifts*` checks.

- Canonical Personskat JSON has an additive, read-only
  [Danish result summary](../../examples/danish-income-tax/personskat-validity.md#læs-dit-gemte-resultat-på-dansk).
  It preserves the model's validity gate, all assessment controls/caveats and
  case diagnostics; invalid cases do not expose diagnostic totals as usable
  tax. Exact integer parsing and formatting are shared with the existing
  conditional-report viewer. Neither viewer authenticates saved output or
  establishes complete legal coverage. No model types, fingerprints, tax
  formulas or existing CLI contracts change; no template migration is needed.

- Personskat adds `PersonskatSocialpensionsudbetaling` for ordinary Danish
  disability, senior and early public pensions and explicit old-regime payment
  components. Taxable income is supplied after ATP/SUPP exclusion, before tax;
  covered exempt components stay out of income. These are not wage or PBL §20
  payout inputs. Unknown/out-of-scope cases withhold a valid comparison.
  Regenerate fingerprinted templates and update exhaustive union consumers;
  collection paths are unchanged. See the [Danish guide](../../examples/danish-income-tax/personskat-socialpension.md).

- Personskat adds `PersonskatFolkepensionsudbetaling` to the existing benefit
  collection. Ordinary Danish folkepension, pension supplement and elder cheque
  enter non-AM personal income; source-classified personal/heating/health
  supplements remain tax-free. These receipts do not become PBL §20 payouts
  for the extra pension deduction. Unknown/out-of-scope cases fail closed.
  Regenerate fingerprinted templates and update exhaustive union consumers.
  Existing collection paths are unchanged; see the [folkepension guide](../../examples/danish-income-tax/personskat-folkepension.md).

- Personskat additionally accepts `PersonskatUddannelsesstøtte` in the existing
  benefit collection, distinguishing ordinary Danish SU grants from SU loans.
  Grants compose as non-AM personal income without employment deductions or
  LL §9 C phaseout income; loans do not become income. Unknown categories and
  cases outside the explicit domestic/no-correction boundary fail closed.
  Regenerate fingerprinted templates and extend exhaustive union consumers;
  existing collection paths are retained. The [SU guide](../../examples/danish-income-tax/personskat-su.md)
  explains source facts, limitations and independent 2025 observations.

- Personskat adds `PersonskatLovbestemteDagpenge` to the existing personal-
  income benefit list and two commuting-result flags:
  `aftrapningsindkomst_afklaret` and `lavindkomsttillæg_afklaret`. Regenerate
  fingerprinted templates before transferring reviewed facts; exhaustive
  consumers of the benefit union must handle the new alternative. Documented
  statutory benefits now compose into LL §9 C income without new wage AM,
  and business income uses the annual AMBL §§4–5 basis. A positive generic
  A-kasse payment may now withhold comparison until its statutory category is
  known, unless the deduction is independently known to be zero. The internal
  deduction/commuting helpers additionally require the annual business result.
  This is a Preview tax-model source/behavior/contract correction, not a change
  to language semantics. See [input and migration guidance](../../examples/danish-income-tax/personskat-dagpenge.md).

- The Danish annual-report reconciliation model now includes separately
  reported additions to assessed tax in both refund and tax-owed checks.
  `tillæg_til_slutskat` and `tillæg_til_slutskat_komplette` move from
  `betaling.restskat` to `betaling`; `RapportRestskat` now holds only the
  observed principal. Update authored constructors and regenerate calculation
  templates before transferring reviewed observations. Refund inputs also
  require explicit additions/completeness; unknown completeness withholds
  settlement and payout rather than assuming zero. This Preview model
  source/contract correction does not change language semantics. See the
  [report-audit migration guide](../../examples/danish-income-tax/aarsopgoerelse-afstemning.md#existing-templates).

- `runa schema --format compact-json` opts into a separate lossless
  `futuruna.calculate.compact.v1` wire representation. Repeated field-source
  objects and ordered source lists are shared, without dropping provenance.
  Default expanded JSON and the complete logical schema fingerprint are
  unchanged; existing template, workbook and cache formats are unchanged.
  Consumers must explicitly support the compact wire schema or retain the
  default format. Schema export accepts `json` and `compact-json`; other
  schema formats are rejected.

- Calculation JSON inputs now reject duplicate object member names at every
  nesting level, including escaped-equivalent names. The same check applies to
  canonical JSON workbook cells and template hydration. Earlier versions could
  silently retain the last supplied value. This is a Preview input-integrity
  bug fix: callers must supply one unambiguous value per member. Ordinary
  language JSON builtins are unchanged.

- `runa call` now fails closed on undefined numerical values and missing value
  rules, including dependencies evaluated during calculation initialization.
  Integer overflow and division/remainder by zero, non-finite Float results,
  assertions, and invalid list access become case diagnostics rather than
  fabricated values or an aborted batch. Valid cases retain input order in
  serial and parallel batches. Typed Boolean predicate misses remain `False`,
  including captured RuleScope predicates, without granting proof certificates.
  This is a Preview behavioral bug fix; models relying on an empty/zero
  fallback for undefined arithmetic or a partial value rule must explicitly
  model the unsupported input (for example, with an optional or result type).
  Ordinary execution and exact-Explore proof authority are unchanged.

- Explore's checked dependency closure now recognizes the documented
  `trim(String) -> String` result. Endpoint proofs preserve exact trimmed text
  (including Unicode whitespace) and leave unknown strings unknown. This
  restores certification of payment-identity helpers without changing their
  runtime behavior or admitting non-String arguments, shadowed builtins, or
  reachable partial operations. Existing proof-obligation tags are unchanged;
  the new trim obligation is additive. No source migration is required.

- Calculation input workbooks now use adapter v7: only collection sheets reached
  by the supplied cases are generated. Full canonical metadata remains present;
  `template --all-tables` retains the exhaustive inspection layout. Complete v6
  workbooks remain readable, but older binaries cannot read v7. Refresh with
  `template --input cases.xlsx --output refreshed.xlsx` after selecting a new
  variant or adding parent items, then complete the new entry sheets. `call`
  rejects cases requiring ungenerated sheets; refresh never repairs deleted
  declared sheets, stale contracts, or invalid facts. See
  [typed calculations](../reference/calculations.md#generate-input).

- `runa explore` and authored exploration queries remain **Experimental**.
  Finite relations can vary income and commuting distance together, retain
  one-unit transitions, ask named questions, and publish separate results and
  mechanism evidence. Exact regional proofs can close ranges without evaluating
  each point; unresolved work remains explicit. This is deterministic compiler,
  arithmetic, and proof machinery, not an LLM-based evaluator.
- Explore persists an authenticated journal and incrementally published
  artifacts. Recovery has explicit pinned-checkpoint and result-row trust
  options for previously checked evidence. They are trust decisions, not new
  independent verification; full computational snapshots and instant restoration
  are not promised. Keep matching source/binary provenance and checkpoint
  evidence. Do not assume experimental journals or output schemas are compatible
  across arbitrary compiler revisions.
- Case-support publication uses the v5 projection envelope. Completed concrete
  classification can publish exact per-question counts without claiming that
  its independent symbolic-support frontier is closed. Such summaries bind
  their extensional selected-question seal and report a null
  `support_evidence_root`; certified summaries still require sealed support.
  Projection identities are versioned so existing v4 output cannot be silently
  appended to under the changed authority contract. Preserve old output and
  checkpoint provenance; do not reuse a v4 publication directory with v5.
- Deferred collection producers still enforce initialized import prefixes when
  preparing execution. An imported immutable binding cannot capture a later
  declaration in its importer merely because stream preparation can see the
  whole checked graph. Put that dependency in the imported source or an earlier
  shared dependency. Invalid members and open RuleScopes fail when consumed.
- Resource containment preserves at least 20% of host CPU and memory under
  its automatic policy. The supervisor is currently macOS-only; experimental
  acceleration and bounded native fanout have narrower supported shapes than
  the general concrete executor.
- A closed supervisor heartbeat has a bounded guardian-exit settlement window.
  Remaining workers are stopped before waiting, and residual groups must still
  be contained before an exit is accepted. Ordinary watchdog iterations no
  longer spend a full settlement window waiting on a still-running worker.
- Late support-observation aliases belong to the refreshed manifest rather
  than the append-only registration stream's presentation identity. Adding a
  demand can therefore reuse authenticated earlier records. This changes that
  artifact's presentation digest; earlier experimental output with the old
  digest is rejected, not silently appended to. Keep the old output and use a
  fresh publication directory with its matching journal. FIND/result target
  renames and changed existing artifact addresses still fail closed.
- The [income-cliff workbook](../../examples/danish-income-tax/exploration-workbook.md)
  records the completed 2026 income/distance grid and its model assumptions.
  It is research evidence about the encoded model, not individual tax advice.
  The Explore CLI and internal module tests cover discovery, replay, publication,
  proof boundaries, and resource admission.
