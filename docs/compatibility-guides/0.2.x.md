# Futuruna Compatibility Guide: 0.2.x

This guide records the changes delivered with 0.2.0 relative to 0.1.1.
The [compatibility policy](../compatibility-policy.md) defines the categories;
[feature stages](../feature-stages.md) remain the authority for maturity.

## Stable Surface Changes

No stable surface is promoted or intentionally removed by this release.
Package metadata, CLI version output, citation metadata, and website version
labels advance together to 0.2.0.

### Post-release assertion messages

`assert_with_message(Bool, String) -> ()` is an additive runtime builtin.
Its two arguments are evaluated eagerly in both interpreted and native code.
False stops ordinary execution or becomes a case-local `runa call` diagnostic;
the supplied message is preserved as text, not interpreted as a format string.
Existing one-argument `assert` is unchanged. This does not add proof authority
or make partial rules total. Programs using the new builtin need a compiler
built after this addition; the original 0.2.0 release does not provide it.
Shadowable registry builtins now also respect lexically typed callable values,
not only named function declarations; native code previously could emit the
builtin instead of the local closure. The assertion regression covers both.
Native builtin templates substitute only their original placeholders: text
such as `{1}` inside an argument is no longer reinterpreted as another
substitution, which could previously corrupt the generated Rust.

## Deprecations

None introduced by this release.

## Bug-Fix Exceptions

- Personskat checks current-year property-tax retirement assertions against
  the owner's and current cohabiting spouse's respective birth dates, using
  the dated social-pension §1a model and ESL §25 year-end test. Contradictory
  status or achievement dates now withhold the annual comparison with a
  field-specific expected date/status; source facts and diagnostic amounts
  are not rewritten. The check covers both ownership directions, even when
  the other person owns no property. No-property and ground-tax-only cases
  do not acquire irrelevant current-year age requirements. The owner's own
  2024 rebate basis also checks the same owner's birth date, assessed for
  2024 rather than the current year; contradictions now withhold comparison
  even when the property is rented out today. Its optional-JSON field error
  identifies the property and the inner age field. A historical spouse,
  acquired rebate basis and survivor succession retain separate source
  identities and are not authenticated by this check. This is a Preview model
  behavioral correction, not a compiler change. Updated source-linked field help changes the
  fingerprint: generate a fresh template and transfer reviewed facts, never
  patch a saved hash. See the [intake boundary](../../examples/danish-income-tax/personskat-validity.md#folkepensionsalder-og-ejendomsskat).

- Source commands such as `runa check`, `run`, and `build` now require an
  explicit filename. Omitting it no longer opens a REPL and reports success
  on end-of-input. Pass `src/main.runa` in an initialized project; these
  commands do not infer a manifest entry. Directory arguments receive an
  actionable usage error, with phase `usage` in `check --json`. Plain `runa`
  still opens the REPL, and directory-aware commands retain their behavior.
  This corrects reviewer issue #68. Missing Rust tools also explain the
  native requirement and the frontend/interpreter alternatives (#66), without
  changing the structured backend-failure contract.

- Concurrent `runa run` and `runa build` invocations now compile in separately
  claimed workspaces, preventing same-named entrypoints from overwriting or
  caching one another's executable. Native reuse goes through the validated
  compiler/source-graph cache; the unkeyed temporary binary cache is removed.
  Cache disabling and overrides therefore cover every executable reuse path.
  Cargo projects also receive separate source and target directories, and a
  failed copy to the requested build output reports failure. These corrections
  address reviewer issues #63 and #64. Existing temporary cache files are not
  deleted or trusted; generated Cargo directory names are internal artifacts.

- Common malformed foreign syntax now carries an actionable hint: comment
  delimiters, single-quoted strings, digit separators, conditional/return/
  binding keywords, guard commas, Prolog arrows and negation, range notation,
  and arrow lambdas. Character-string recovery reports the opening quote once.
  Valid identifiers, character literals, type declarations such as `# TODO`,
  literal string braces, operator continuations and opaque Rust are preserved.
  These diagnostic improvements address part of reviewer issue #61; they do
  not add digit separators, percentage literals or a new comment grammar.

- A misplaced or repeated `@ sprog` / `@ language` declaration now reports
  its own source location and asks to move it first. It no longer silently
  leaves the file in its initial lexical mode. Valid initial headers accept
  whitespace and trailing comments. In Danish mode, `og` and `eller` now use
  the existing `and` / `or` semantics, including precedence, short-circuiting
  and rule-goal bindings; English `or` is also available. This addresses
  reviewer issue #59. Use different identifiers for bindings named `og` or
  `eller` in Danish files. English-mode identifiers are unchanged.

- Ordinary calls now reject undeclared rule arities, known scalar callees and
  arguments that contradict an ordinary function's declared parameter type.
  Resolution follows lexical binders, so an untyped callback does not inherit
  an unrelated outer function's contract. Known receivers reject nonexistent
  fields and methods, including `items.length` and `items.map(...)` on lists.
  Use `length(items)` and `map(items, callback)` instead. Missing fields on
  untyped receivers fail at the access during interpretation; they no longer
  become `()`. Actual unit-valued fields, tuple projections and bound methods
  remain valid. These corrections address reviewer issue #56; inferring field
  requirements for untyped rule parameters before execution remains tracked
  separately in `td-a539f8`.

- Unsupported effect invocations now fail frontend checking with a source
  location, before either execution backend runs. This fixes reviewer issue
  #54, where `@ println(...)`, `@ log(...)`, `@ printf(...)` and `@ assert(...)`
  could silently do nothing in the interpreter. Use `@ print(...)` for output
  and ordinary `assert(...)` / `assert_with_message(...)` calls for assertions.
  Unchecked interpretation also reports unknown effects explicitly. Supported
  effects, localized aliases, declaration markers and algebraic calls retain
  their existing behavior.

- Exceptions require a label followed by a named rule call. A missing label
  such as `| exception rate(x) -> 10` now fails during parsing with a correction
  hint; write `| exception reduced rate(x) -> 10`. The same validation applies
  to Danish `undtagelse`. Bare names and other expressions cannot be exception
  heads; spell a nullary call `rate()` and remove parentheses around a head.
  This fixes reviewer issue #53, where malformed exceptions could silently
  disappear from dispatch and leave the default result in force.

- Rules with safely known Boolean results now return `False` on a miss even
  when their guarded parameters are unannotated. For example,
  `| eligible(age) -> True under age >= 18` returns `False` for `eligible(10)`
  in both interpreted and compiled execution. Native parameter inference also
  considers guards. This fixes reviewer issue #52; invalid guard evaluations
  still fail, and partial non-Boolean families retain their existing behavior.
  The runtime fallback has separate metadata from the stricter proof
  certificate, so it does not invent parameter schemas or totality evidence.

- A single `=` inside an expression now fails during parsing with a comparison
  hint at that token. Use `==` in conditions, rule guards, lambda bodies and
  other comparisons. `=` remains valid for bindings, type declarations and
  named arguments. This fixes reviewer issue #51: earlier binaries could
  reinterpret the expression as equality only in compiled execution. Invalid
  programs now stop before either backend runs or performs earlier effects.

- VS Code syntax colors now cover `----` quotation blocks, character literals,
  triple-quoted templates and interpolation, rule/verification runes and rule
  keywords. Comparisons retain operator colors beside function calls. Both
  accepted Boolean spellings remain highlighted; completion suggests canonical
  `True`/`False`. This addresses reviewer issue #50 without changing the lexer
  or the meaning of source programs. Tokenizer regressions run in a separate
  editor CI job; see the [editor guide](../../editors/vscode/README.md).

- Editor completion after `.` offers known fields of that receiver, including
  partial field names, local bindings, typed parameters, nested/generic records,
  and imported schemas. Field hover reports the owner and declared field type;
  ordinary completion lists each record name once. Unknown receivers do not
  inherit unrelated global suggestions. This addresses reviewer issue #49.
  The editor uses a temporary parsed member name without modifying the buffer.
  These are type hints, not program validation: unrelated syntax errors can
  prevent suggestions, and variant-specific fields need narrowing evidence
  before they can be offered safely.

- `runa lsp` accepts case-insensitive framing headers and reports malformed
  JSON with `ParseError` while continuing at the next complete frame.
  Unsupported requests, including unadvertised pull diagnostics, return
  `MethodNotFound`; unknown notifications receive no reply. Initialization is
  required once, shutdown rejects further requests, and `exit` or a closed
  input stream without prior shutdown returns status 1. Missing, invalid,
  duplicate or truncated framing and output failures stop with a transport
  error instead of silently succeeding. These editor protocol corrections
  address reviewer issue #48 without changing language evaluation.

- Redeclaring an ADT now replaces stale constructor schemas and variants in
  frontend checking, including a user-defined `Pair` replacing the prelude
  type. Constructors shared by different nominal types remain distinct.
  Posthoc `@ export TypeName` accepts type names, and qualified named-call
  arguments are checked as argument values rather than internal parser calls.

- Return annotation checks retain the native unit result of `push` on an
  `inout List` or `inout shared List` parameter. Ordinary persistent `push`
  retains its list result, and local or callable shadowing still applies.
  This preserves the native mutation contract; interpreter `inout` parity
  remains a separate limitation tracked in the release triage.

- Editor parse errors now produce separate diagnostics at their actual source
  locations, with hints retained and an empty range for end-of-file errors.
  This fixes reviewer issue #45. Editor positions use zero-based UTF-16 units;
  CLI JSON retains one-based Unicode scalar columns.

- Editor hover, completion and go-to-definition now interpret cursor positions
  as UTF-16 units, and definition ranges measure identifiers in those units.
  Danish and non-BMP names retain the correct widths; completion no longer
  slices inside UTF-8 characters. This fixes reviewer issue #46 without
  changing compiler spans or CLI columns.

- Editor import checking decodes UTF-8 percent escapes in local file URIs,
  including Danish directory names. Definition links encode Unicode and
  reserved filename characters. Ordinary go-to-definition now follows plain
  imports, including transitive imports, while retaining local declarations
  and bounding cyclic traversal. This addresses reviewer issue #47; general
  lexical and qualified-member navigation remains a separate editor limitation.

- Ordinary interpreted user faults now stop with exit code 1 and a Futuruna
  source diagnostic, replacing Rust panic text and exit code 101. Completed
  effects are preserved; later effects do not execute. Helper failures point
  to their invoking expression, while imported initialization errors retain
  the imported source. Internal panics, native executable reporting, and
  calculation/exploration failure contracts remain distinct. CLI status and
  diagnostic colors respect the output terminal, `NO_COLOR`, and `TERM=dumb`;
  authored output is unchanged. `runa check --json` adds a versioned structured
  report with source locations and explicit backend-validation status. These
  changes address reviewer issue #44; see [CLI diagnostics](../cli-diagnostics.md)
  for the report schema and location limits.

- Unknown unqualified type names in annotations now fail frontend checking,
  including in unused functions, record fields, rule heads and local bindings.
  For example, change the typo `Intt` to `Int`, or declare the intended type.
  The diagnostic names the Futuruna source instead of a generated Rust cache
  file. This addresses reviewer issue #43; lower-case generic variables,
  forward declarations, imported types, and explicit Rust declarations/uses
  retain their existing meaning. Qualified Rust paths and names supplied by
  wildcard imports or opaque Rust macros remain subject to backend checking.
  This does not provide a general source map for all Rust compiler errors.

- Diagnostics inside triple-quoted interpolation now retain the embedded
  expression's source position, including Unicode columns and CRLF input.
  Constructor-pattern errors point to the pattern instead of the arm body.
  Legacy name lookup ignores quoted prose and comments and uses character
  columns, including when locating import paths. These corrections
  address reviewer issue #42. The internal `MatchArm` AST now carries
  `pat_span`; source and execution behavior are unchanged. Diagnostic metadata
  is excluded from the existing structural representation, preserving
  content-addressed definition identities and hash imports.

- Rule guards now require Boolean results. Known invalid guards fail frontend
  checking without a call, and dynamically supplied invalid values stop
  evaluation rather than silently rejecting a candidate or selecting a
  fallback. Known incompatible result types within a rule family are also
  diagnosed before execution, including across plain imports. Independent
  scopes and arities, partial collection types, and supported exception-only
  families remain valid. These checks address the type-safety reports in
  reviewer issue #41; unknown dynamic types remain subject to runtime checks
  and do not provide proof or totality guarantees.

- Imported function bodies now receive frontend checking. Plain imports use
  the collected declaration environment; qualified modules retain their own
  scope, including private helpers and explicit dependencies. Errors retain
  the imported file's path and source position in CLI and library diagnostics.
  Editors receive an import-site diagnostic with a link to the original
  location. Shared dependencies do not duplicate the same error, and cyclic
  import traversal remains finite. This corrects reviewer issue #40; files
  previously accepted only because their imported bodies escaped checking can
  now fail before execution or Rust generation.
  Shared nullary constructor names do not acquire the parent of the last
  imported enum during diagnostic inference; known nominal field mismatches
  remain errors.

- Unknown source characters and unclosed strings, character literals,
  triple-quoted templates, or `----` quotation blocks now reject the file
  before execution. Diagnostics identify the offending character or opening
  delimiter instead of silently dropping text. Adjacent expressions such as
  `= x = 5 5` require a newline or `;`; existing explicit rune boundaries,
  effect invocations and block boundaries remain accepted. Embedded Rust
  retains its own literal/comment grammar, and a missing closing Rust brace
  is also rejected. Formatting malformed source leaves the file unchanged.
  These corrections address reviewer issues #38 and #39. The internal token
  enum now carries lexical errors and opaque Rust bodies; low-level literal
  reader signatures are unchanged.
  A newline after a complete Rust `::*` import remains a statement boundary;
  the wildcard does not trigger arithmetic continuation.

- Calculation input decoding now reports independent field errors together
  instead of stopping at the first one. This includes nested records,
  collections, selected variants, and duplicate set values. Invalid cases
  still produce no result, while valid cases keep their results and order.
  An invalid container or unknown variant stops validation of that subtree.
  Template hydration reports errors across cases before writing an artifact.
  This corrects reviewer issue #36. The Rust `decode_input` method retains its
  single-error signature; `decode_input_diagnostics` exposes the complete set.

- Calculation input workbooks now use XLSX schema version 8. Empty strings
  are represented by `""`; strings beginning with a quotation mark use JSON
  string quoting. Ordinary text stays literal, and blank cells still mean
  missing required input or an absent optional value. The encoding also
  preserves empty strings in lists, sets, map values, and map keys. This
  corrects reviewer issue #35 without accepting formulas. Versions 6 and 7
  remain readable with their original text semantics; refresh writes version
  8. Earlier binaries reject version 8. Previously lost empty text cannot be
  recovered from a blank cell without new input.

- `length` accepts lists and strings. Known unsupported operands now produce
  a frontend diagnostic, including in `schema`, `template`, and `call`;
  dynamically supplied invalid values fail instead of returning zero.
  Use `map_len` and `set_len` for maps and sets. String lengths retain Unicode
  scalar counting, and authored functions or local callbacks named `length`
  retain their own contracts. This corrects reviewer issue #34. Unknown
  generic operands still require runtime validation; this does not add general
  higher-order type inference. The Rust `list_length` helper likewise rejects
  non-list values rather than reporting zero.

- A bare source filename such as `runa main.runa` now resolves relative
  imports from the current directory, just like `runa ./main.runa`.
  Checking, emitting, calculation schemas, and audits share that behavior.
  The library resolver also treats an empty source directory as `.`.
  This corrects reviewer issue #33; nested imports still resolve relative
  to their containing source file.

- Verification now encodes non-ASCII function, type, constructor, and field
  names consistently in SMT, including constructor tests in match expressions.
  Names resembling the reserved encoding prefix remain distinct. String
  encoding preserves quotes, literal backslashes, control characters, and
  Unicode text instead of letting those characters alter SMT syntax or value.
  This corrects reviewer issue #32. Literal characters above U+2FFFF remain
  explicitly unverified by the current SMT Strings theory; see the
  [SMT-LIB alphabet and escaping rules](https://smt-lib.org/theories-UnicodeStrings.shtml).

- `runa verify` now returns success only when the file contains invariants,
  every invariant is proved, and authored explicit proofs have no validation
  failures. Counterexamples, unsupported or unknown results, missing or failed
  Z3 execution, and an empty invariant set return exit status 1. A successful
  SMT fallback does not hide a failed explicit proof. Solver process status
  and diagnostics are checked before accepting `unsat`; models are requested
  only after `sat`. This corrects reviewer issue #31 so verification can gate
  CI. Kernel-only proofs still work without Z3.

- The experimental topology audit reports conflicting values from ordinary
  zero-argument rule clauses at the same priority, including two unconditional
  numeric outcomes. Its explanation includes the outcome chosen by source
  order. Boolean clauses remain alternative ways to satisfy a predicate, and
  different arities are separate rule calls. This corrects reviewer issue #30
  and avoids reporting conflicts between unrelated overloads. The audit still
  evaluates the current zero-argument environment; it is not an exhaustive
  proof over parameterized rule inputs.

- Interpreted imports now initialize top-level `~` stream bindings, including
  exported subjects and private bindings used by exported helpers. A plain
  imported subject retains its messages across repeated imports, matching the
  native downstream consumer. This corrects reviewer issue #29.
  Named module imports expose their initial stream values too; updating those
  subjects through a qualified field still has a retained interpreter/native
  gap (`td-fd9122`) and is not covered by the plain-import parity claim.

- `runa fmt` preserves string and character literals, `----` source quotations,
  and embedded Rust blocks verbatim. It no longer splits the `<-` send operator
  or changes literal values and quoted law text through indentation or spacing.
  Before writing, formatting checks token content and parsed structure;
  invalid syntax or an unexpected structural change returns a nonzero status
  and leaves that file unchanged. Directory formatting reports any failed
  files, including in `--check` mode. This corrects reviewer issue #28.
  Intentionally malformed parser fixtures are checked separately in the
  formatter regression suite: they must be rejected and left unchanged.

- The injected prelude no longer causes local declarations to be registered
  ahead of their prefix imports. Local function definitions override imported
  functions, while rule clauses retain imported-before-local ordering within
  each dispatch priority. The normal interpreter now matches no-prelude and
  native execution for these cases. SMT namespace resolution likewise applies
  local function overlays before checking duplicate names. This corrects
  reviewer issue #27; qualified namespaces remain separate. Prelude injection
  carries explicit internal provenance, so an identical authored declaration
  is not mistaken for compiler-supplied code. Verification rejects a plain
  import after local declarations or executable statements: its static symbol
  graph cannot represent source-ordered rebinding. Such scripts still have a
  retained interpreter/native parity gap; place plain imports at the start of
  the file for the shared verified behavior.

- `runa verify` now checks integer arithmetic against the checked `i64`
  runtime domain. Overflow, division by zero, and `MIN / -1` or `MIN % -1`
  are counterexamples to a claimed guarantee, not assumptions that remove
  executions from consideration. Division truncates toward zero and remainder
  follows the dividend's sign. Obligations follow selected branches, match
  guards, strict local values, and supported helper calls.
  This corrects reviewer issue #26. A mathematical kernel proof involving
  arithmetic now needs semantic verification before the CLI reports a proof;
  an unchecked arithmetic lemma is not registered for subsequent proofs.
  Opaque arithmetic and recursive arithmetic helpers can remain unsupported.
  Float claims are explicitly unsupported until the verifier models runtime
  floating-point semantics; exact SMT reals do not establish such a proof.
  Consequently some formerly reported proofs now need Z3, report a
  counterexample, or remain unsupported. This does not change runtime values.

- A map constructed with `map_new` and `map_insert` now retains the key and
  value types supplied by the insertion, so `map_get(map, key) ?: fallback`
  checks the actual value type. Collection element inference also preserves
  generic parameters, nullable layers, references, function types, and unit.
  This corrects reviewer issue #25: valid defaults are accepted, and
  incompatible defaults still fail with their concrete types. Authored
  functions retain priority over same-named collection builtins.
  Native `map_get`, `map_get_or`, and `map_contains` also preserve the key
  type instead of forcing string conversion. Integer and Boolean keys work,
  and owned or borrowed string keys remain reusable without extra key copies.

- Authored functions and methods now check known body result types against
  their return annotations in the frontend. Checks follow return branches,
  local bindings, and contextual list, constructor, and closure results;
  generic parameters remain rigid inside their declaring function. A
  contradiction reports the offending expression before interpretation or
  Rust compilation. This corrects reviewer issue #24. Fix the body or its
  annotation to express the intended result. This does not turn partial
  inference for external or otherwise unresolved expressions into a proof
  of type correctness or execution safety.

- Interpreted functions and closures now have an operational nesting limit of
  128 active calls, separate from the existing rule-call limit. Exceeding it
  reports incomplete evaluation with the function name instead of exhausting
  the CLI stack. The counter is restored after returns and failures; flat
  callback iteration does not consume cumulative depth. Synchronous `poll`
  callbacks use ordinary function dispatch and its declaration environment.
  This corrects reviewer issue #23. Deep recursive list processing can use
  iterative collection builtins such as `map` and `foldl`; this change does
  not add tail-call optimization or change native recursion behavior.

- `format_float` explicitly validates precision in both execution paths.
  Negative precision and values above the formatter's supported maximum of
  65535 now report a Futuruna argument error; calculations and ground
  expressions retain typed failure channels. Valid formatting, including zero
  and maximum precision, keeps its output and argument evaluation order.
  This corrects reviewer issue #22 without silently clamping the input.

- Interpreted `json_object` now uses JSON parsing and serialization for keys
  and values, matching native execution. Quotes, backslashes, and control
  characters are escaped; malformed JSON-looking text becomes a string rather
  than corrupting the object. Valid JSON text retains its existing meaning:
  supply quoted JSON text when a numeric-looking or Boolean-looking value
  must stay a string. Object output is normalized and duplicate keys retain
  the last value, as in the native backend. This corrects reviewer issue #21.

- The frontend now checks match coverage through nested constructor fields and
  their combinations. Guarded arms do not establish unconditional coverage;
  complete nested alternatives and unguarded fallbacks remain valid. Partial
  matches fail at their source location, and unchecked runtime matches report
  an error instead of returning `()`. This corrects reviewer issue #20. Add
  the missing cases or an explicit unguarded fallback; coverage analysis does
  not prove that an arbitrary guard always holds.

- Ordinary integer arithmetic now rejects overflow and division/remainder by
  zero in both the interpreter and native output, regardless of optimization
  or Rust overflow-check settings. Negation, integer `abs`, `sum_list`, and
  integer stream `sum` use the same checked domain. Valid integer results are
  unchanged; ordinary execution stops and calculations retain case-local
  diagnostics. This corrects reviewer issues #18 and #19. Programs depending
  on wrapped values or zero for undefined arithmetic must explicitly model
  those inputs, for example using a result type. Float zero-divisor behavior
  is a separate boundary and is not changed by this integer correction.

- Interpreted string ordering, character comparisons, Float remainder, and
  tuple/unit equality now produce their values instead of `()`, including
  equality of tuples and units inside named records. Shared expected-output
  tests require successful interpreter and native execution. An `if` condition
  must return `Bool`; invalid conditions and unsupported operator operands
  now fail explicitly instead of selecting a branch or supplying `()`.
  This corrects reviewer issue #17. Mixed Int/Float equality is not newly
  admitted by this correction.

- Invariants with a known non-Boolean predicate type now produce a located
  frontend error at declaration time, even if no `?` statement evaluates them.
  Boolean invariants retain ordinary pass/failure handling and forward checks.
  Unchecked calculation and ground-expression evaluation report a typed user
  error instead of classifying a non-Boolean predicate as an internal panic.
  This corrects reviewer issue #16. Replace an invalid value expression with
  the Boolean property the invariant is intended to check.

- Nested interpreted rule calls now have an operational depth limit of 128.
  Exceeding it reports incomplete evaluation instead of overflowing the
  runtime stack or pretending a recursive query returned `False`. The guard
  restores the caller's depth after returns and failures, including typed
  calculation and ground-expression failures. This corrects reviewer issue
  #15; it does not add tabling or prove that a cyclic relation has no witness.
  The separate enumeration depth bound remains in place.

- Rule-body `and` separators now behave like commas at every goal position.
  `or` and `||` form independent alternatives, with conjunction binding more
  tightly. Each branch checks and evaluates its own existential bindings;
  names from another branch are not available there. Nested calls and
  parenthesized expressions retain ordinary Boolean `and`/`or` semantics.
  This corrects reviewer issue #14 without requiring changes to valid comma
  conjunctions.

- Interpreted enumeration and existential queries now apply exceptions before
  guarded defaults and ordinary clauses, retaining first-applicable order
  within each override tier. A false override excludes the candidate; a true
  override can supply a finite candidate even without an ordinary fact.
  Queries return the input template's value rather than the override's return
  value. Decisions use complete argument rows and declaration scopes, and
  selected clause bodies are not evaluated again to check their priority.
  Queries that need unresolved positive head values to establish priority
  report incomplete evaluation. This corrects reviewer issue #13; no source
  migration is needed for finite Boolean rule queries.

- Interpreted rule-goal conjunctions no longer carry anonymous `_` bindings
  from one goal to another. Direct named rule calls with `_` now perform
  existential search, including single-goal bodies and calls inside `not(...)`,
  instead of matching `_` as a value. This corrects false conjunctions
  and false claims that no matching fact exists (reviewer issues #2 and #12).
  Named variables still share their bindings. This is a behavioral bug-fix
  exception for wrong rule results; no source migration is required.

- Grounded Boolean predicates in interpreted `findall` bodies now use normal
  expression evaluation. Builtins such as `not` and `contains`, authored
  functions, and nested calls can filter candidates instead of silently
  eliminating every answer. A grounded predicate contributes an answer only
  when it returns `True`, and its arguments are evaluated once per candidate.
  This corrects reviewer issue #3; no source migration is required for Boolean
  predicates. Enumeration with free variables has separate remaining defects
  tracked in the [0.2.3 review record](../releases/0.2.3-reviewer-triage.md).

- Interpreted `findall` now binds every named free argument in a body goal
  before advancing to the next goal. Each later argument is constrained by
  the earlier bindings, so a pass-through relation retains its answers and a
  join cannot combine an owner from one fact with an item from another.
  Anonymous arguments introduce no shared binding, repeated names must agree,
  and already-bound argument expressions are captured once. This is the
  behavioral wrong-result correction for reviewer issue #4, with no source
  migration required.

- Interpreted existential queries now use the same argument-binding search as
  `findall`, so derived relations can supply witnesses and later goals can
  backtrack through them. Bound literal and constructor head terms are checked
  before a clause body runs; derived answers can contain constructor fields
  supplied by the body. Rule-local names use the declaration's scope without
  capturing same-named globals, and enum constructors remain values rather
  than becoming free variables. This corrects reviewer issues #5 and #11;
  no source migration is required. Native parity and the remaining query work
  are recorded in the 0.2.3 review record.

- Interpreted recursive enumeration now fails explicitly when its existing
  depth limit is exhausted, rather than returning an incomplete list or
  letting an incomplete search support a Boolean answer. Ordinary evaluation
  reports a runtime error; guarded calculations and exploration retain their
  typed failure channels. This is a wrong-result correction for reviewer issue
  #6. It does not add tabling or remove the operational recursion bound.

- Interpreted `findall` now deduplicates answers by runtime value equality,
  including tuple fields and constructor ownership, instead of printed text.
  Integer `1` and string `"1"` therefore remain distinct answers. The existing
  distinct-answer behavior and first-discovery order remain in place; this
  corrects reviewer issue #7 without changing the query syntax.

- Builtin `findall` and `search` now reject non-variable templates with a
  source-located frontend error. The supported form is `findall(item,
  relation(item))`; tuple, list, constant, and computed templates no longer
  silently produce an empty result. Unchecked interpretation also reports a
  runtime failure. Custom callables with these names keep ordinary call
  resolution and are not subject to the builtin template restriction. This
  is the invalid-program correction for reviewer issue #8.

- Interpreted rule heads now match signed numeric literals, unit, and list
  terms structurally. List lengths and elements must agree, variables inside
  lists bind locally, and enumeration retains signed/list head values.
  Unsupported computed patterns are rejected by the frontend and report a
  runtime failure if unchecked code reaches them. They no longer act as
  wildcards. This corrects reviewer issue #9; move computations into the rule
  body or a guard when migrating an invalid computed head.

- Native rule heads now retain signed numeric and list types, compare exact
  list lengths and elements, and bind typed list elements inside constructor
  patterns. Ground signed/list facts can be enumerated without a string-typed
  ABI. Native Boolean rule alternatives also preserve `or`/`||`, grouping,
  and short-circuiting instead of emitting a conjunction. These are behavioral
  bug fixes for #9 and #14; no source migration is required. Derived existential
  queries and untyped pattern inference still have separately tracked native
  limitations; this does not claim full rule-query parity.

- Repeated names in interpreted rule heads now require equal values, including
  occurrences nested in constructors, tuples, and lists. Repeated query
  positions in `findall` share constraints across facts, derived rows, and
  finite typed domains. Bindings propagate through structural head terms
  before later goals run, preserving argument evaluation counts and excluding
  mismatched rows before later effects. Rule-local names also shadow matching
  names in lexical parent frames. This is the wrong-result correction for
  reviewer issue #10; no source migration is required.

- Native repeated head variables now constrain later positions instead of
  rebinding them, with independent Rust parameter names. Typed scalar and
  supported structural heads, repeated ground-fact query positions, and
  repeated finite-enum template positions preserve those constraints. Scalar
  Float comparisons retain the interpreter's epsilon rule. Zero-argument
  existential clauses can search a checked, complete ground-fact relation.
  Native enumeration rejects incomplete fact-table sources rather than
  returning only their materialized rows. These are behavioral bug fixes;
  derived queries and structural Float comparison remain limited. An
  existential clause capturing an outer value is explicitly rejected until
  its lexical binding contract is aligned (`td-38e94c`); pass the value as an
  explicit rule parameter in the meantime.

- Ordinary `match` expressions now compile string-literal patterns through
  value comparisons instead of emitting invalid Rust expressions as patterns.
  This includes text nested in constructor fields and tail-recursive matches.
  Literal matching precedes user guards, the subject is evaluated once, and
  fallback bindings keep their existing ownership behavior. This repairs the
  stable native behavior contract; no source migration is required. Regression
  coverage includes escaped/Unicode text and generated-name collision cases.

- Inline modules expose their locally declared rule families as callable
  members, matching native execution and qualified imports. The interpreter
  previously omitted registry-only rules from module bindings, producing unit
  instead of a value; a surrounding collection operation could hide that as a
  successful zero. Member calls retain the declaring namespace and do not
  expose parent-only rules. Calculations additionally reject non-callable
  callee values instead of suppressing the runtime error. This is a behavioral
  wrong-result fix, with calculation and interpreted/native regression coverage.

- The shared frontend rejects known `List + List` operands. `+` has never
  implemented list concatenation: native code rejected it, while the interpreter
  could yield unit and a surrounding `length` could silently report zero.
  Use `concat(left, right)` instead. Calculation invocation also rejects
  unsupported arithmetic operands at runtime, including indirect expressions
  whose operand types are not statically resolved. Numeric addition and string
  concatenation are unchanged. This is a source/behavioral bug-fix exception,
  covered at the frontend, calculation, diagnostic and differential boundaries.
- Structural map/set keys retain lexical display-key iteration order across
  interpreter and native execution. Lookup and equality still use structural
  identity; distinct keys that print alike are not collapsed by iteration.
- Ordinary generated Boolean rule calls can establish that their own typed
  head matches, including captured and nullary predicates. A matched false
  clause returns `False`; this does not issue a context-independent miss
  certificate or expand solver/Explore proof authority. Genuine unproven
  misses and partial value families continue to fail closed.
- Backend result typing now includes rule-derived global bindings, string
  concatenation, and exported primitive returns from qualified sources by
  alias and arity. Imported nominal ownership is not erased. Builtin/prelude
  generic constructor signatures are deduplicated by their full field schema.
  Nullary constructors do not acquire distinct identities from a field-layout
  flag. Global bindings and rule results share a bounded inference fixed point;
  forward RuleScope dependencies work without certifying unanchored cycles.
  Nested constructor patterns no longer certify exhaustive coverage merely
  because their outer constructors cover the type's variants.
- Generic constructor-pattern payloads retain their instantiated parent types
  in native code, including named fields and same-spelled constructors owned
  by different types. Builtin `not` retains its Boolean backend result without
  overriding an authored binding or granting a new proof certificate.
- SMT rule-call validation uses the same default `Int` sort for unbound
  invariant variables as the emitted declarations. Existing program bindings
  and nominal constructors are not defaulted. Arithmetic backend typing does
  not prove unbounded integer arithmetic total: verification can report an
  unsupported proof even when a particular concrete call executes correctly.
  Namespace verification fixtures use globally total rules; separate negative
  regressions retain the arithmetic, partial, recursive and higher-order limits.
- Guarded value-rule families need an explicit unconditional fallback when
  the native dispatcher cannot establish exhaustive coverage. Complementary
  user-written guards alone are not a totality certificate. Export graph
  snapshots now include the public constructors exported with their ADT.
- Checked bare constructor resolution now rejects mixed nullary/non-nullary
  spellings even with an expected result type. Runtime value lookup cannot
  select an arity, so treating that ambiguity as an exact nullary value was
  unsound. Give the constructors distinct names. Compiler regression coverage
  keeps both unannotated and annotated uses outside exact proof authority.
- Integer collection `sum` retains its ordinary generated return type inside
  rules and RuleScopes without adding a new exact-proof intrinsic. A plain
  import already flattened at the root also retains its shared nominal owner
  when reached through a qualified module. These repair integration regressions
  caught by the existing newline-layout, import-mesh, and downstream canaries.
  Root/qualified source-order parity and integer-sum regressions are permanent
  unit and differential coverage; the broader cross-parent ownership work
  without a root owner remains tracked separately in `td-625bb9`.
  Interpreter constructor patterns, typed rule heads, equality, and collection
  keys now use plain/hash-import declaration provenance consistently. Separate
  qualified aliases and identical-looking declarations from different sources
  remain distinct; cached collection keys do not depend on root import order.
- Rule dispatch and checked Boolean misses are aligned across the checked
  interpreter, generated Rust, and supported solver lowering. This is a
  behavioral and verification bug-fix exception: an unsound proof or an
  interpreter-only empty-string result for a checked Boolean family is not
  supported behavior. The context-closed boundary and embedder migration are
  described in the [Boolean rule-miss entry](0.1.x.md#2026-08-19-boolean-rule-misses),
  which was recorded during development and ships in this integration.
  Context-sensitive families outside the proven subset retain their documented
  limits. Regression coverage includes `tests/verify_cli.rs`, the
  `tests/fixtures/verify/rule_dispatch_*` fixtures, and compiler unit tests.
- Qualified callable verification preserves module identity, exported/private
  boundaries, and rule-family arity instead of conflating same-named callables.
  Category: verification compatibility; an unsound result may now fail closed.
  Call only exported members through qualified imports. Permanent coverage is
  in the `qualified_namespace_*` verification fixtures and `tests/verify_cli.rs`.

## Database feature removal

The 0.2.3 cleanup intentionally removes language-level database persistence.
This is a source and behavior compatibility break, including the SQLite
functions previously listed in the stable stdlib reference. Existing programs
using them must migrate; this is not a silent implementation substitution.

Removal is immediate rather than a warning-only release: the interpreter's
database stubs could return empty rows or zero without performing the compiled
program's storage operations. Keeping those stubs during a deprecation period
would retain inconsistent execution. This cleanup deliberately removes that
contract instead of expanding the language's database responsibilities.

Removed surfaces:

- `@ store`, `@ persist`, and `@ migrate`;
- fact mutation statements `assert Type(...)`, `retract Type(...)`, and `abort`;
- the database change stream `watch(Type)` and generated change-event types;
- `db_open`, `db_exec`, `db_query`, `db_query_row`, `db_insert`, and `db_close`;
- the intrinsic `Db` type (applications may define their own type with that name);
- automatic SQL schema, transaction, migration, and SQLite dependency generation.

Persistence annotations and mutation statements report an explicit removal
error, including inside function and scope bodies. Removed builtin names no
longer resolve automatically; ordinary functions may use those names. Ordinary
`assert(condition)` remains available. `| scope` continues to own reactive
lifetimes; it no longer implies database transactions. General effects,
streams, actors, pure rules, in-memory logic facts and queries, calculations,
and proofs remain part of the language. Explore's resumable filesystem journal
is independent and remains in place.

Keep storage in the application that invokes Futuruna: read the relevant data,
validate it against a typed calculation contract, evaluate the rule model, and
store the result in the application. The existing `runa schema`, `template`,
and `call` workflows provide that typed boundary. Rust applications can use
Futuruna's existing library/interop boundary. No replacement database package
is included or promised; a future optional integration needs consistent
interpreter/native behavior and a separately tested contract.

Existing database files are not deleted, rewritten, or automatically migrated.
Export any required data with its original application or SQLite tooling before
retiring the old executable. Historical design notes remain under
`docs/persist/`; database-dependent demo sources remain in Git history.
