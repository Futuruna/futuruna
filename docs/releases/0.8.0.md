# Futuruna 0.8.0

Futuruna 0.8.0 generates **conformance cases from the law**: a suite of
input/expected pairs that another implementation of the same law must pass,
with a report of the rule clauses it covers. It also reads more of the law as
it is written: dates are ordered, Option guards are audited, tuple patterns
and constructor patterns in rule heads, and `scan` over a list. Everything
new in this release is Experimental.

## Conformance cases from the law (Experimental)

- **`runa cases model.entry.runa --entry NAME --out DIR`** writes a
  conformance suite another implementation of the law must pass: for each rule
  clause the entry reaches an input that fires it (a Z3 witness of the rule's
  arguments, moved into a seed's or a scenario's input along the
  explanation's provenance), inputs just below, at and just above each integer
  or date threshold of a guard, and the entry calls of `--scenario` files. Each
  `<id>.case.json` holds `id`, `entry`, `kind`, `covers` (the clauses its
  result rests on, with location and cited paragraphs), `input` and `expected`;
  `coverage.json` says "cited rule clauses: X of Y covered" and why each other clause
  has no case. See [Generate conformance cases](../reference/calculations.md#generate-conformance-cases)
  and the RFC [Conformance cases](../rfcs/conformance-cases.md).
- **A rejection covers only what it rests on.** A result variant is a
  rejection when the entry returns the prelude's `Result` (its `Err`) or
  `--rejected VARIANT` names it. Such a case is `kind: "rejected"`, counted
  apart in `coverage.json` (`cases`), and covers only the clauses its
  rejection rests on: the input runs again with each `if` and `match`
  branch's value traced to the condition that chose it, and the clauses the
  rejection's values and conditions come from are its `covers`. A clause that
  fires only in rejected inputs off that path is uncovered, reason
  `rejected`.
- **The law is the cited clauses.** Coverage is headlined by the rule clauses
  with `@ cite` ("cited rule clauses: X of Y covered"); uncited clauses are
  counted apart (`cited`, `uncited`). A rejected case is written only when a
  cited clause is on its rejection's path: a rejection resting only on
  uncited clauses (an overflow guard, a technical bound) is listed under
  `technical` in `coverage.json` with the clauses it rests on, and only the
  guards of cited clauses get boundary cases.
- **A case covers only what its result rests on.** A clause the entry
  evaluates but gives nothing from (a field of a shared step the entry drops)
  is not covered by the case: every result's clauses are read from a decided
  run, as a rejection's are. Decisions no branch makes count too: in a
  decided run, `filter`, `find`, `any`, `all`, `take_while`, `drop_while` and
  `partition` give a value computed from every predicate result they read,
  `flat_map`, `unwrap_or`, `is_some` and `is_none` from the `None` they
  dropped or the Option they tested, a clause's `[]` is recorded as a
  branch's is, and a Boolean rule's `false` when no clause applies rests on
  the guards and bodies that did not hold. So a result that rests on such a
  decision traces back to the rule clauses that made it. A reachable clause
  no result rests on is uncovered, reason `not-in-result`, reported
  (`cited.not_in_result`, `uncited.not_in_result`, "of which N not in the
  result" in the summary) but still counted in the total: a comparison of
  two `Date`s still reads them untraced, so the measurement may miss a
  dependence and must understate. Its guard gets no boundary cases.
- **New list elements.** When a rule's arguments come from a list element (an
  event, a position) and moving it gives no case, `runa cases` appends a new
  element carrying Z3's witness, the rest of it as plain as still holds; its
  key is the case's id, or for an open collection only a key the witness
  gives. It is kept only when the run is not rejected and fires the clause.
- **Only inputs an integrator can send.** A case's input and result are in
  the domain the generated SDK's validators accept: an `Int` within
  ±(2^53 − 1), a `Date` on the calendar (years 0000 to 9999). Z3's witnesses
  keep the inputs a rule's arguments are in it, a run outside it is no case,
  and a clause only such an input fires is uncovered, reason
  `outside-input-domain`; a threshold side outside it has no case.
- **The same cases however loaded the machine.** Every Z3 query of `runa
  cases` (witnesses, boundaries, the searches provenance drives) and of the
  clause audit it starts from, which `runa audit` shares, has a resource
  limit (Z3's `rlimit`, 20 000 000 units, about ten seconds of solving)
  instead of a ten-second time limit: a query is decided, or reported
  undecided, the same way on an idle and on a busy machine, so the same law,
  seeds, scenarios, `runa` and Z3 give the same suite byte for byte. An
  undecided query reads "unknown or resource limit reached".

## Law idioms

- **Dates are ordered.** `<`, `<=`, `>`, `>=` compare two `Date`s
  chronologically in the checker, the interpreter, generated Rust and the SMT
  encoding of `runa verify` and `runa audit`; a partial case reads a comparison
  of an unknown date as unknown. `<` on any other declared type is now a type
  error (it failed in the interpreter). See
  [Comparison](../reference/basics.md#comparison).
- **Option guards are audited.** `runa verify` and `runa audit` read an
  `Option` of any payload (`closed: Date?`) through `is_some`, `is_none`,
  `unwrap_or` and a `match` on `Some`/`None`: a generic function's call is
  translated as its body at the argument's type (before, at `Int` only, so a
  `Date?` guard was "not analyzed"). See
  [runa verify](../reference/runes.md).
- **Tuple patterns.** `match (lost_right, closed) { | (Some(l), None) -> … }`
  matches two values together, in the interpreter and native code; the arms
  are checked for exhaustiveness together, and `runa verify` and `runa audit`
  translate a match on a tuple written in place element by element. See
  [match](../reference/basics.md#match).
- **Constructor patterns in rule heads.** A family whose clause heads cover
  every variant (`| due(y, ChangedBySkat(d)) -> … | due(y, CorrectedByInstitute(r)) -> …`)
  is total: it compiles natively without a fallback clause, and `runa verify`
  and `runa audit` read it as never missing. An exception can match
  `Some(day)` at a `Date?` position and read the day, so no clause needs a
  placeholder date. See
  [Declared result types](../reference/runes.md#declared-result-types-experimental).
  In a partial case, a head pattern (`Some(day)`, `A(n)`) on an unknown input
  makes the clause's applicability unknown: the answer needs that input, and
  what the pattern binds is unknown on the same path (before, the body read an
  unbound name: a failed match, a crash, or a guessed clause). A complete
  case reads the inputs a head pattern matches, so they are not reported
  unused. `runa audit` and `runa verify` test a `None` head pattern and
  qualify a `None` result with its sort, so a family over two Option sorts
  (`Date?` and `Int?`) is analyzed (before, Z3 rejected the query). The same
  holds for `None` compared with (`x == None` is a constructor test) and inside
  a value: a record field (`Span(start = None, …)`), `Some(None)`, or a
  function's or rule's result. A head or `match` pattern reads each field by
  its constructor, so a field two constructors give different sorts
  (`Deposit(…, purpose: DepositPurpose?)`, `Withdrawal(…, purpose:
  WithdrawalPurpose?)`) is read (before, Z3 rejected the query on the unknown
  `runa_field_purpose`), and a `match` arm reads a constructor with named
  fields by position (`| Deposit(amount, purpose) -> …`; before, Z3 rejected
  the unknown `runa_field_Deposit_f0`).
- **`scan` over a list.** `scan(bookings, opening, |cash, b| cash + signed(b))`
  is the state after each booking, a list as long as `bookings`, in the
  checker, the interpreter, native code and WebAssembly (before, the
  interpreter returned a stream and native code typed the step as `Int`). It
  is the stream `scan` with the same arguments; decide each state with a rule
  (`map(scan(...), |cash| overdrawn(cash))`), which `runa audit` analyzes. A
  guard that scans a list itself is "not analyzed", as one with `foldl` is. See
  [Running state over a list](../reference/runes.md#running-state-over-a-list).
- **An `Option` is not a list.** A `flat_map` callback that returns an
  `Option` is a type error naming the fix (`[x]` for `Some(x)`, `[]` for
  `None`); one known only at run time stops the program in the interpreter,
  native code and WebAssembly. Before, the interpreter read every such result
  as an empty list, dropping each `Some` (`flat_map([30, 70, 140], |x| if x <
  100 { Some(x) } else { None })` summed to 0), while native code and
  WebAssembly kept it (100). The same held for an `Option` given to `map`,
  `filter`, `flat_map` and the other operations with a callback as their list
  (`map(Some(1), |x| x + 1)` was `[]` in the interpreter, `[2]` in native
  code): it is now a type error too, and an `Option` known only at run time
  stops `map`, `filter` and `flat_map` in the interpreter. See
  [Collection Operations](../reference/stdlib.md#collection-operations-kotlin-inspired).

## Audit: clauses shadowed with a different result (Experimental)

- **`runa audit` separates conflicting shadowing from redundancy.** An
  unreachable clause whose inputs an earlier clause of its tier takes and, for
  some input, decides differently is reported as `Shadowed with a different
  result`: two clauses rule on the same facts with different results, settled
  silently by source order. The report names the clause, the clauses that take
  its inputs, the clause source order selects, a witness input and both
  results there. A clause shadowed by clauses that give the same result stays a
  plain unreachable clause. The findings line and the `--json` summary count
  the new finding (`shadowed_with_different_result`), and its JSON finding
  carries `shadowed_by`, `selected`, `witness` and `results`. See
  [Auditing clause reachability](../reference/runes.md#auditing-clause-reachability).

## Verify quantifies over records

- **`runa verify` quantifies free variables over records.** A free variable
  passed to a rule, function, or constructor parameter typed with a record (a
  non-generic type with one constructor) whose fields are Int, Bool,
  payload-free enums, or such records now ranges over every value of that
  record, instead of making the claim unsupported. Rule cascades over a whole
  record (`| f(a: Fund): Bool -> a.x == Ja`) verify without a helper rule
  taking one parameter per field; every Int field is a 64-bit value, and a
  counterexample prints the record in source syntax, such as
  `a = Fund(x: Ja, y: Nej, n: 0)`. Records with other field types (such as
  String) stay unsupported with a diagnostic naming the field. See
  [Three assurance levels](../reference/runes.md#three-assurance-levels).

## Native code

- **A named pattern may name some of the fields.** `| Deposit(purpose: p) ->`
  on a constructor with more fields compiles natively (before, the generated
  Rust did not compile: "pattern does not mention field `amount`").
- **A head pattern binds a whole field at its declared type.** In
  `| exception funded paid(Deposit(amount, purpose)) -> True under purpose ==
  Some(Funding)`, `purpose` is a `DepositPurpose?`, so the guard compiles
  natively (before, the binder was typed `DepositPurpose`, and native code
  refused the rule as unsafe).
- **Callers read a rule family over constructor patterns natively.** A rule
  that calls a family whose clause heads match every variant
  (`| level(First) -> Supreme`, `| level(Second) -> High`, …) compiles
  natively also when the caller's name sorts before the family's. Such a
  caller compared or returned the family's result without unwrapping it, and
  the generated Rust did not compile (`expected Option<Court>, found Court`).
- **A local binding named like a builtin is a value.** A lambda binder,
  parameter, or local binding named `ln`, `exp`, `abs`, `sqrt`, `show`,
  `length` or another builtin is captured by inner closures like any other
  binding, so `flat_map(xs, |ln| map(ys, |c| R(ln = ln, c = c)))` compiles
  natively (before, the generated Rust did not compile: "cannot move out of
  `ln`, a captured variable in an `FnMut` closure").

## Explore

- **A successor can call a polymorphic helper.** A helper whose signature
  uses a type variable, such as `> others(all: List(a), current: a) ->
  List(a)`, can be called from the helpers of an Explore transition:
  `transition after in neighbours(before)` with `neighbours` returning
  `map(others(all_kinds, row.kind), |kind| Row(kind = kind, n = row.n))`
  explores to an exact closure. Each call is typed by binding the type
  variables from its arguments, so `others(all_kinds, row.kind)` has the type
  `List(Kind)` there. Before, `runa explore` refused the query with
  `checked exploration boundary is unavailable:
  Producer(SemanticDependencyClosureUnsealed { layer: "relation", ... })`. A
  call whose result type its arguments do not fix (such as a call of
  `> nothing(n: Int) -> List(a)`) is still refused.
