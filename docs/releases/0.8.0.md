# Futuruna 0.8.0 (unreleased)

Futuruna 0.8.0 reads more of the law as it is written: dates are ordered,
Option guards are audited, tuple patterns and constructor patterns in rule
heads, and `scan` over a list. Everything new in this release is
Experimental.

## Law idioms

- **Dates are ordered.** `<`, `<=`, `>`, `>=` compare two `Date`s
  chronologically in the checker, the interpreter, generated Rust and the SMT
  encoding of `runa verify` and `runa audit`; a partial case reads a comparison
  of an unknown date as unknown. `<` on any other declared type is now a type
  error (it failed in the interpreter). See
  [Comparison](../reference/basics.md#comparison).
- **Option guards are audited.** `runa verify` and `runa audit` read an
  `Option` of any payload (`closed: Date?`) through `is_some`, `is_none`,
  `unwrap_or` and a `match` on `Some`/`None`: a generic function's call is
  translated as its body at the argument's type (before, at `Int` only, so a
  `Date?` guard was "not analyzed"). See
  [runa verify](../reference/runes.md).
- **Tuple patterns.** `match (lost_right, closed) { | (Some(l), None) -> … }`
  matches two values together, in the interpreter and native code; the arms
  are checked for exhaustiveness together, and `runa verify` and `runa audit`
  translate a match on a tuple written in place element by element. See
  [match](../reference/basics.md#match).
- **Constructor patterns in rule heads.** A family whose clause heads cover
  every variant (`| due(y, ChangedBySkat(d)) -> … | due(y, CorrectedByInstitute(r)) -> …`)
  is total: it compiles natively without a fallback clause, and `runa verify`
  and `runa audit` read it as never missing. An exception can match
  `Some(day)` at a `Date?` position and read the day, so no clause needs a
  placeholder date. See
  [Declared result types](../reference/runes.md#declared-result-types-experimental).
  In a partial case, a head pattern (`Some(day)`, `A(n)`) on an unknown input
  makes the clause's applicability unknown: the answer needs that input, and
  what the pattern binds is unknown on the same path (before, the body read an
  unbound name: a failed match, a crash, or a guessed clause). A complete
  case reads the inputs a head pattern matches, so they are not reported
  unused. `runa audit` and `runa verify` test a `None` head pattern and
  qualify a `None` result with its sort, so a family over two Option sorts
  (`Date?` and `Int?`) is analyzed (before, Z3 rejected the query). The same
  holds for `None` compared with (`x == None` is a constructor test) and inside
  a value: a record field (`Span(start = None, …)`), `Some(None)`, or a
  function's or rule's result. A head or `match` pattern reads each field by
  its constructor, so a field two constructors give different sorts
  (`Deposit(…, purpose: DepositPurpose?)`, `Withdrawal(…, purpose:
  WithdrawalPurpose?)`) is read (before, Z3 rejected the query on the unknown
  `runa_field_purpose`), and a `match` arm reads a constructor with named
  fields by position (`| Deposit(amount, purpose) -> …`; before, Z3 rejected
  the unknown `runa_field_Deposit_f0`).
- **`scan` over a list.** `scan(bookings, opening, |cash, b| cash + signed(b))`
  is the state after each booking, a list as long as `bookings`, in the
  checker, the interpreter, native code and WebAssembly (before, the
  interpreter returned a stream and native code typed the step as `Int`). It
  is the stream `scan` with the same arguments; decide each state with a rule
  (`map(scan(...), |cash| overdrawn(cash))`), which `runa audit` analyzes. A
  guard that scans a list itself is "not analyzed", as one with `foldl` is. See
  [Running state over a list](../reference/runes.md#running-state-over-a-list).
