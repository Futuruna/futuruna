# Futuruna 0.4.0

Futuruna 0.4.0 is in development; this file collects its release notes.
Everything new in this release is Experimental unless a section says
otherwise.

`runa call --explain` returns with every result where each amount came from:
the rule clause that produced it, the exception that applied, the law section
and the paragraphs the clause cites with their quoted text, and the rules and
inputs it was computed from.

## Explanations (Experimental)

- **`runa call --explain`.** Every case result gains `explanation.values`:
  each leaf of the result by its output path (the path syntax of needs), with
  `by` (the rule clause, the input path of a value passed on unchanged, a
  computation outside any rule, or a constant) and `from` (the nearest rules
  and inputs it was computed from, with their values, at most 32).
  `explanation.sections` holds each law section an explained clause sits in:
  its location, quoted documents, metadata attachments and quote.
- **`--explain=full`** lists every contributor and adds `derivation`, the
  whole tree of rule nodes behind the reported values.
- **Partial cases.** `runa call --partial --explain` explains every
  `Complete` result. `--explain` is refused with `--partial=check`, and
  writes JSON only.
- **Results unchanged.** A case's `result` is byte for byte the one
  `runa call` gives without `--explain`; the tax engine's cases and needs
  interviews are compared in both modes.
- **No cost when off.** Values carry provenance only in explained cases; an
  unexplained case creates no traced value (a test counts them).
- **`runa schema --format explanation`** prints the explanation's JSON
  Schema.

## Paragraph citations (Experimental)

- **`--@cite:§ 9, stk. 3--`** above a rule clause names the paragraphs it
  implements; several are separated by `;`, `nr. N` names an item and
  `in <source>` a quoted document. A citation on a rule's first clause covers
  its other clauses that have none.
- **Checked.** `runa check` finds each cited paragraph in the quote of the
  section around the clause (`§ N.`, `Stk. N.` and `N)` lines) and rejects a
  paragraph the quote does not hold, naming the paragraphs it does hold. A
  citation outside a law section or not above a rule clause is an error too.
- An explanation shows a cited paragraph's quoted text verbatim; a clause
  without a citation shows its section.

## Explanations in the WebAssembly engine and the TypeScript SDK (Experimental)

- `Model.callExplained(entry, input, full?)` and
  `Model.callPartialExplained(entry, input, full?)` return the documents of
  `runa call --explain` and `runa call --partial --explain`. Source locations
  are relative to the model root.
- `runa sdk ts` generates `<entry>Explained` and `<entry>QueryExplained`, the
  `Explanation` types, and the optional transport methods `callExplained` and
  `callPartialExplained` (see the TypeScript SDK below for their paths).

The design is [Explanations](../rfcs/explanations.md).

## Partial cases and needs (Experimental)

- **A need names the rule of the law it waits for.** `waiting_rule` is the
  innermost rule or function on the stack when the path was first read that
  is declared in a law section (one whose quote holds a `[sources/...]`
  document), else in any section with a quote, not the validation helper or the entry
  that happened to read it. Such a need also carries the `section` and the
  `paragraphs` cited on the clause being tried (an exception's own
  citation), on the rule's first clause, or on the function. Without a
  sectioned frame, `waiting_rule` is the innermost rule family, or the entry,
  as before.
- **Citations on functions.** `--@cite` may stand above a function
  (`> f(...)`) inside a section.
- `runa schema --format partial-result` and the TypeScript SDK's `Need` type
  gain the optional `section` and `paragraphs`.

## TypeScript SDK reads as TypeScript (Experimental)

`runa sdk ts` generates TypeScript that a TypeScript team would write by hand,
while the engine keeps its JSON: the SDK encodes each case before a call and
decodes the result and the needs after it. See
[Calculations](../reference/calculations.md#typescript-sdk).

- **camelCase fields.** `opening_cash_ore` is `openingCashOre` in the types,
  the validators, the partial cases, `setAt` and the resolver patterns; it
  stays `opening_cash_ore` on the wire. Two fields of one record or variant
  with the same camelCase name are an error.
- **Enums are strings.** A sum type whose variants carry no fields is a string
  union: `direction: "Deposit"` instead of `{ $variant: "Deposit" }`. A sum
  type with payload variants stays a union tagged by `$variant`, a name no
  field can take.
- **Dates are ISO strings.** A `Date` is `"2026-03-01"` (`IsoDate`), validated
  as a day on the calendar, and `{ year, month, day }` on the wire.
- **Needs at TypeScript paths.** `need.path`, `unusedPaths` and an entry
  need's `subject` are the paths a TypeScript caller writes:
  `events[0].amountOre`, an enum at its own path (`events[0].direction`) and a
  date as a whole (`events[0].date`, one need for the date's parts). The
  partial types write an unknown variant as `Unknown<T>`.
- **One shared runtime.** `setAt`, `resolve`, the paths, the needs, the calls,
  the wire codec and the error classes are generated once into a runtime
  module that every entry imports; `--runtime ../runtime.ts` lets the SDKs of
  several source files share one copy. Each entry generates only its types,
  validators, codecs, path tables and functions.
- **Wire codecs.** `schema.ts` has a codec per record and union, and
  `<entry>Entry` names an entry's input and result codecs; `toWire`,
  `fromWire` and `fromWirePath` convert `runa call` documents and paths; a
  field a codec does not know throws `WireError`, so a result that arrives with
  TypeScript names instead of the engine's is an `output` error.
- **Explanations at TypeScript paths.** `<entry>Explained` and
  `<entry>QueryExplained` decode the explanation with the entry's codecs: its
  values are keyed by TypeScript paths of the result, an input it names is at
  its TypeScript path in the case, a `Date` is one value (its ISO date) and
  `from_omitted` is `fromOmitted`. A need carries `waitingRule`, `section` and
  `paragraphs`.

## Field metadata on declarations (Experimental)

- **`@ field(...)`.** A calculation input field's label, question, help, unit,
  sources and providing entry are written on the field's declaration:
  `# Owner(@ field(label = "Fully tax liable") fully_tax_liable: Bool)`.
  Written before a `#` data type, it describes every input field of that type,
  such as an enum's field or the `$variant` column of a sum with payloads.
  Values are plain strings (`help = "..."`, not `Some("...")`) and no metadata
  record type or `path` is declared.
- **Same contract.** `runa schema` emits the same `field_metadata` entries as
  metadata listed by path; only the provenance (`anchor`, `binding`) names the
  declaration, so the schema fingerprint changes once when a model moves its
  metadata. Workbooks, needs and the TypeScript SDK read it unchanged.
- **One precedence rule.** An exact path for one calculation (anchored field
  records with a string, `pathof` or input-rooted `refof` path) beats a field's
  declaration or `refof(Type::field)` projection, which beats a type's
  default. Two declarations at the winning level are an error naming both.
- **Labels in context.** A label written for a type or its field reads
  `<record field label>: <label>` below a labelled record field, so `Date`'s
  `year` is labelled once and appears as `Trade date: year`. A required record
  field may now be named by exact metadata too, for its label.
- **Diagnostics.** `runa check` reports unknown and repeated keys, a missing
  label, `entry` without `subject`, two `@ field` on one field or type, an
  `@ field` that no field or data type follows, and values that are not
  strings or lists. For both metadata forms, a provided field's `subject` must
  now be an input path holding the providing entry's input type.

Specified in [Field metadata on declarations](../rfcs/field-metadata.md).

## Unit types (Experimental)

- **Declaration.** `# unit Ore "DKK øre"` declares a unit of measure for
  whole numbers. The description says what the unit counts. `unit` is
  contextual and stays an ordinary name elsewhere; it has no Danish keyword.
  Units exist for `Int` only.
- **Arithmetic.** `Ore + Ore`, `Ore - Ore`, `Ore % Ore` and `-Ore` are `Ore`;
  `Ore * n`, `n * Ore`, `Ore / n` and `Ore % n` are `Ore`; `Ore / Ore` is a
  plain `Int`. `Ore * Ore`, `n / Ore`, mixing two units, and adding or
  comparing `Ore` with a named plain `Int` are type errors whose messages name
  the fix.
- **Literals.** A number written in the source takes the unit its place
  requires: `amount > 0`, `amount + 100`, an `Ore` field given `0`, a match
  arm `| None -> 0` beside an `Ore` arm and `= amounts: List(Ore) = [0, 100]`
  need no conversion.
- **Callbacks.** The parameter of a `map`, `filter`, `foldl` or other
  collection callback has the element type, so a wrong unit inside the
  callback is caught, and `sum_list(map(xs, |x| x.amount))` keeps the unit.
- **Conversions.** `Ore(n)` gives a plain `Int` the unit and `Int(amount)`
  takes it off; a change of unit is a function that uses both. `abs`,
  `min_int`, `max_int`, `clamp`, `sum` and `sum_list` keep the unit.
- **Runtime unchanged.** The interpreter, `runa call` JSON, `runa verify` and
  generated Rust see plain `Int`; generated Rust declares `pub type Ore = i64;`.
- **Contract.** `runa schema` adds `"unit": "Ore"` to primitive `Int` type
  references with a unit and a top-level
  `"units": [{"name": "Ore", "description": "DKK øre"}]`. Field metadata of a
  unit-typed field takes its `unit` text from the declaration; an authored
  `unit = Some(...)` on such a field is an error.
- **TypeScript SDK.** A unit is a branded number type: `runa sdk ts` declares
  `export type Ore = number & { readonly __unit: "Ore" }` in `types.ts`, with
  the unit's description as TSDoc, and `OreSchema` and `ore(n)` (a safe
  integer, else a `RangeError`) in `schema.ts`. Every `Ore` field, result,
  path table entry, `setAt` value and resolver answer is an `Ore`, so a bare
  number or a `Micro` there is a type error; plain `Int` stays `number`. The
  wire value is the same number.
- **Folds and rule families.** `foldl` with a literal start takes the unit
  when its step adds a value of exactly one unit
  (`foldl(items, 0, |total, item| total + item.amount)` is `Ore`); write
  `Ore(0)` only when the step adds no unit value. A rule family may mix literal
  clauses (`-> 0`) with unit clauses and has the unit; such a family, a
  RuleScope member and a function over a unit are generated as Rust over `i64`.

Specified in [Unit types for whole numbers](../rfcs/unit-types.md); reference
in [Unit](../reference/runes.md#unit).

## Constructor names scoped to their type (Experimental)

- **Shared constructor names.** Two sum types in one scope may declare the
  same constructor name, such as `Trade` in `Event` and in `AskYearEvent`. A
  use takes its owner from the type the context expects: a pattern from the
  matched value, an argument, field or result from its declared type, one side
  of `==` from the other side.
- **`Type.Constructor`.** An expression or a pattern can name the owner
  explicitly: `AskYearEvent.Trade(...)`, `| AskYearEvent.Closed -> ...`.
- **No guessing.** A shared name with nothing to give it a type is an error
  that names the owners and the explicit spellings; the owner is never chosen
  by arity or by field names.
- **Data keeps the declared names.** `$variant` in calculation JSON, contracts,
  `runa schema`, displayed values and solver models use the name the
  declaration wrote, and so do generated Rust enums (`AskYearEvent::Trade`).
  The WebAssembly engine runs such models as `runa call` does. Programs
  without shared names are unchanged.

See [the RFC](../rfcs/scoped-constructors.md).

## Compatibility

- **Runtime values.** The interpreter's `Value` gains a `Traced` variant; an
  exhaustive `match` on `Value` in Rust code using the library must cover it.
- **TypeScript SDK names.** `<entry>Explained`, `<entry>QueryExplained` and
  the explanation types are generated names; a contract type of the same name
  must be renamed to use the SDK.
- Output without `--explain` is unchanged: `explanation` is left out.
- **Needs.** `waiting_rule` may name a different, outer rule than before for a
  model with law sections; `section` and `paragraphs` are new optional
  fields. A client that keyed on the old `waiting_rule` must accept the new
  value; `runa call --partial` is Experimental.
- **TypeScript SDK.** Code written against the 0.3 SDK changes with it: field names are camelCase,
  enum values are strings, dates are ISO strings, need paths are TypeScript
  paths, and `unused_paths`, `waiting_rule`, `attachment_path` and a
  diagnostic's `case_id` are `unusedPaths`, `waitingRule`, `attachmentPath`
  and `caseId`. Partial unions use `Unknown<T>` for `{}`, and an enum or a
  date has no `Partial` type of its own.
- `runa sdk ts` writes `runtime.ts` next to the entry modules unless
  `--runtime` names another place. A contract type named like a runtime
  export (`Unknown`, `IsoDate`, `Codec`, …) or `<Type>Codec` must be renamed.
- The SDK's changes leave `runa call`, `runa call --partial` and the
  contracts unchanged.
- **Field metadata.** For both metadata forms, `runa check` now rejects a
  provided field whose `subject` is not an input path holding the providing
  entry's input type. Moving metadata onto declarations changes the schema
  fingerprint once (only the provenance differs).
- **Units in the SDK.** TypeScript code that writes a plain number into a
  field whose contract type has a unit must make it with the unit's
  constructor (`ore(1200)`) or take it from another value of that unit.

## Known issues

- Explanations are an interpreter feature; compiled programs do not explain.
- A single value a rule returns unchanged from a deeper rule or the input is
  reported for the outer rule, with the deeper rule or the input in `from`.
