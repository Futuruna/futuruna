# Futuruna 0.4.0

Futuruna 0.4.0 is in development; this file collects its release notes.
Everything new in this release is Experimental unless a section says
otherwise.

`runa call --explain` returns with every result where each amount came from:
the rule clause that produced it, the exception that applied, the law section
and the paragraphs the clause cites with their quoted text, and the rules and
inputs it was computed from.

## Explanations (Experimental)

- **`runa call --explain`.** Every case result gains `explanation.values`:
  each leaf of the result by its output path (the path syntax of needs), with
  `by` (the rule clause, the input path of a value passed on unchanged, a
  computation outside any rule, or a constant) and `from` (the nearest rules
  and inputs it was computed from, with their values, at most 32).
  `explanation.sections` holds each law section an explained clause sits in:
  its location, quoted documents, metadata attachments and quote.
- **`--explain=full`** lists every contributor and adds `derivation`, the
  whole tree of rule nodes behind the reported values.
- **Partial cases.** `runa call --partial --explain` explains every
  `Complete` result. `--explain` is refused with `--partial=check`, and
  writes JSON only.
- **Results unchanged.** A case's `result` is byte for byte the one
  `runa call` gives without `--explain`; the tax engine's cases and needs
  interviews are compared in both modes.
- **No cost when off.** Values carry provenance only in explained cases; an
  unexplained case creates no traced value (a test counts them).
- **`runa schema --format explanation`** prints the explanation's JSON
  Schema.

## Paragraph citations (Experimental)

- **`--@cite:§ 9, stk. 3--`** above a rule clause names the paragraphs it
  implements; several are separated by `;`, `nr. N` names an item and
  `in <source>` a quoted document. A citation on a rule's first clause covers
  its other clauses that have none.
- **Checked.** `runa check` finds each cited paragraph in the quote of the
  section around the clause (`§ N.`, `Stk. N.` and `N)` lines) and rejects a
  paragraph the quote does not hold, naming the paragraphs it does hold. A
  citation outside a law section or not above a rule clause is an error too.
- An explanation shows a cited paragraph's quoted text verbatim; a clause
  without a citation shows its section.

## Explanations in the WebAssembly engine and the TypeScript SDK (Experimental)

- `Model.callExplained(entry, input, full?)` and
  `Model.callPartialExplained(entry, input, full?)` return the documents of
  `runa call --explain` and `runa call --partial --explain`. Source locations
  are relative to the model root.
- `runa sdk ts` generates `<entry>Explained` and `<entry>QueryExplained`, the
  `Explanation` types, and `ExplainingTransport`, a transport with
  `callExplained` and `callPartialExplained` (see the TypeScript SDK below for
  their paths).

The design is [Explanations](../rfcs/explanations.md).

## Partial cases and needs (Experimental)

- **A need names the law that waits for it.** `waiting` lists every rule or
  function of a law section (one whose quote holds a `[sources/...]`
  document) that read the fact on the evaluated paths, speculation included,
  each with its `section` and cited `paragraphs`; when some of them cite
  paragraphs, only those are listed, so an uncited helper (a rounding
  function, a validation check) that read the fact first no longer stands
  for the law. Without a law section it falls back to a section of checks,
  the innermost rule, then the entry.
- **Acts, not bare paragraphs.** Each cited paragraph names its quoted
  document (`source`) and the document's `act` (`title`, `identifier`,
  `url`), read from the header block at the top of the document under
  `sources/` (`Title:`, `Document identifier:`, `Human-readable URL:`), in
  needs and in explanations.
- **What lies behind an unknown condition.** `needs` are the facts that block
  the result as it stands; the promise is no longer "every fact that
  blocks". `later` lists the facts evaluation read only behind an unknown
  condition it could not decide, which answering the needs may make needs.
- **Fewer rounds.** `sort` reads only what its comparisons reach, so a list
  sorted by a known key and position stays a known list carrying its unknown
  fields; a function over it still runs and the facts it reads are needs in
  the same round. A recursion under an unknown condition is cut only when it
  depends on an unknown condition of its own, so a helper that splits a known
  list runs behind an unknown `if` as it does in every completion. `any`,
  `all` and `find` read their function's answers in Kleene logic: `any` with
  a `True` answer is `True` and `all` with a `False` answer is `False` past
  unknown answers, and an undecided scan needs every unknown answer, not only
  the first.
- **List elements by key.** `@ field(label = "ISIN", key = True)` makes a
  `String` or `Int` field the key of its type (`definitions[].key` in the
  contract): a field of a record, or of a sum type's variants when every
  variant declares the same key field with the same type (an event's `id`);
  `runa check` names a variant without it, or with another name or type. A
  need inside such a list element carries `keys`:
  `[{path: "opening_positions[0]", field: "isin", value: "IE..."}]`.
- **A date is one fact.** A need for a `Date`'s year, month or day is one
  need at the date's path, with the date field's own metadata; `runa schema`
  now emits that metadata (label, question, help) for a required `Date`
  field, which it dropped before.
- **Citations on functions.** `--@cite` may stand above a function
  (`> f(...)`) inside a section.
- `runa schema --format partial-result` types `waiting`, `keys` and `later`.

## What decided, and what a result rests on (Experimental)

- **`because`.** An explained value a rule clause produced lists what the
  guards that chose the clause were computed from: its own guard and those of
  the clauses above it that were tried. In the tax engine's
  `ask-closed-owner-died-2026`, `deposit_room_ore = 0` by the exception
  `closed` is there because of the account's ending. Guards are still read
  untraced; results do not change. A literal a `match` arm chose is now
  computed from the matched value (so `is_some(x)` from what `x` holds),
  where an explanation used to call it `Constant`.
- **`assumptions`.** An explanation lists the `Assumption` attachments of the
  sections whose rule clauses fired, and of the entry's own section, instead
  of a model listing every assumption in its result: a section whose rules
  did not apply adds none.

## TypeScript SDK reads as TypeScript (Experimental)

`runa sdk ts` generates TypeScript that a TypeScript team would write by hand,
while the engine keeps its JSON: the SDK encodes each case before a call and
decodes the result and the needs after it. See
[Calculations](../reference/calculations.md#typescript-sdk).

- **camelCase fields.** `opening_cash_ore` is `openingCashOre` in the types,
  the validators, the partial cases, `setAt` and the resolver patterns; it
  stays `opening_cash_ore` on the wire. Two fields of one record or variant
  with the same camelCase name are an error.
- **Enums are strings.** A sum type whose variants carry no fields is a string
  union: `direction: "Deposit"` instead of `{ $variant: "Deposit" }`. A sum
  type with payload variants stays a union tagged by `$variant`, a name no
  field can take.
- **Dates are ISO strings.** A `Date` is `"2026-03-01"` (`IsoDate`), validated
  as a day on the calendar, and `{ year, month, day }` on the wire.
- **Needs at TypeScript paths.** `need.path`, `unusedPaths` and an entry
  need's `subject` are the paths a TypeScript caller writes:
  `events[0].amountOre`, an enum at its own path (`events[0].direction`) and a
  date as a whole (`events[0].date`, one need for the date's parts). The
  partial types write an unknown variant as `Unknown<T>`.
- **One shared runtime.** `setAt`, `resolve`, the paths, the needs, the calls,
  the wire codec and the error classes are generated once into a runtime
  module that every entry imports; `--runtime ../runtime.ts` lets the SDKs of
  several source files share one copy. Each entry generates only its types,
  validators, codecs, path tables and functions.
- **Wire codecs.** `schema.ts` has a codec per record and union, and
  `<entry>Entry` names an entry's input and result codecs; `toWire`,
  `fromWire` and `fromWirePath` convert `runa call` documents and paths; a
  field a codec does not know throws `WireError`, so a result that arrives with
  TypeScript names instead of the engine's is an `output` error.
- **Explanations at TypeScript paths.** `<entry>Explained` and
  `<entry>QueryExplained` decode the explanation with the entry's codecs: its
  values are keyed by TypeScript paths of the result, an input it names is at
  its TypeScript path in the case, a `Date` is one value (its ISO date) and
  `from_omitted` is `fromOmitted`. A need carries `waiting`: the rules that
  wait for it, each with its `section` and cited `paragraphs`.

## Field metadata on declarations (Experimental)

- **`@ field(...)`.** A calculation input field's label, question, help, unit,
  sources and providing entry are written on the field's declaration:
  `# Owner(@ field(label = "Fully tax liable") fully_tax_liable: Bool)`.
  Written before a `#` data type, it describes every input field of that type,
  such as an enum's field or the `$variant` column of a sum with payloads.
  Values are plain strings (`help = "..."`, not `Some("...")`) and no metadata
  record type or `path` is declared.
- **Same contract.** `runa schema` emits the same `field_metadata` entries as
  metadata listed by path; only the provenance (`anchor`, `binding`) names the
  declaration, so the schema fingerprint changes once when a model moves its
  metadata. Workbooks, needs and the TypeScript SDK read it unchanged.
- **One precedence rule.** An exact path for one calculation (anchored field
  records with a string, `pathof` or input-rooted `refof` path) beats a field's
  declaration or `refof(Type::field)` projection, which beats a type's
  default. Two declarations at the winning level are an error naming both.
- **Labels in context.** A label written for a type or its field reads
  `<record field label>: <label>` below a labelled record field, so `Date`'s
  `year` is labelled once and appears as `Trade date: year`. A required record
  field may now be named by exact metadata too, for its label.
- **Diagnostics.** `runa check` reports unknown and repeated keys, a missing
  label, `entry` without `subject`, two `@ field` on one field or type, an
  `@ field` that no field or data type follows, and values that are not
  strings or lists. For both metadata forms, a provided field's `subject` must
  now be an input path holding the providing entry's input type.

Specified in [Field metadata on declarations](../rfcs/field-metadata.md).

## Unit types (Experimental)

- **Declaration.** `# unit Ore "DKK øre"` declares a unit of measure for
  whole numbers. The description says what the unit counts. `unit` is
  contextual and stays an ordinary name elsewhere; it has no Danish keyword.
  Units exist for `Int` only.
- **Scale.** `# unit Ore "DKK øre" = DKK / 100` also says that 100 `Ore` make
  one `DKK`; `= 1 / 1000000` scales a plain number. The base is a name of its
  own or `1`, never a declared type or unit, so every unit of one base names
  the base itself.
- **Arithmetic.** `Ore + Ore`, `Ore - Ore`, `Ore % Ore` and `-Ore` are `Ore`;
  `Ore * n`, `n * Ore`, `Ore / n` and `Ore % n` are `Ore`; `Ore / Ore` is a
  plain `Int`. `Ore * Ore`, `n / Ore`, mixing two units, and adding or
  comparing `Ore` with a named plain `Int` are type errors whose messages name
  the fix. `[a] == [m]` and `Some(a) == Some(m)` compare the units inside and
  are errors when they differ.
- **Literals.** A number written in the source takes the unit its place
  requires: `amount > 0`, `amount + 100`, an `Ore` field given `0`, a match
  arm `| None -> 0` beside an `Ore` arm and `= amounts: List(Ore) = [0, 100]`
  need no conversion.
- **Callbacks.** The parameter of a `map`, `filter`, `foldl` or other
  collection callback has the element type, and `foldl`'s accumulator has the
  type of the start value, so a wrong unit inside the callback is caught, and
  `sum_list(map(xs, |x| x.amount))` keeps the unit. A closure bound to a name
  (`= f = |x| x + a`) is checked again at each call with the types of its
  arguments. A callback whose parameter type is not known (a closure that is
  never called, a lambda passed to a function of your own) is still judged
  only where its types are known.
- **Conversions.** `Ore(n)` gives a plain `Int` the unit and `Int(amount)`
  takes it off. Between two units of one base, `to(MicroDkk, amount)` converts
  exactly when it multiplies, and a conversion that divides names its rounding:
  `to_nearest(Ore, amount)` (halves away from zero), `to_floor`, `to_ceiling`
  or `to_toward_zero`. A missing rounding, or one on a conversion that does
  not round, is a type error. Elaboration writes each conversion as its `Int`
  arithmetic, so the interpreter, the solver and generated Rust run the same
  rounding. A change between units of different bases is a function that
  uses `Int(...)` and the unit. `abs`, `min_int`, `max_int`, `clamp`, `sum`
  and `sum_list` keep the unit.
- **Runtime unchanged.** The interpreter, `runa call` JSON, `runa verify` and
  generated Rust see plain `Int`; generated Rust declares `pub type Ore = i64;`.
- **Contract.** `runa schema` adds `"unit": "Ore"` to primitive `Int` type
  references with a unit and a top-level
  `"units": [{"name": "Ore", "description": "DKK øre", "scale": {"of": "DKK", "per": 100}}]`;
  `scale` is present only for a unit that declares one. Field metadata of a
  unit-typed field takes its `unit` text from the declaration; an authored
  `unit = Some(...)` on such a field is an error.
- **TypeScript SDK.** A unit is a branded number type: `runa sdk ts` declares
  `export type Ore = number & { readonly __unit: "Ore" }` in `types.ts`, with
  the unit's description as TSDoc, and `OreSchema` and `ore(n)` (a safe
  integer, else a `RangeError`) in `schema.ts`. Every `Ore` field, result,
  path table entry, `setAt` value and resolver answer is an `Ore`, so a bare
  number or a `Micro` there is a type error; plain `Int` stays `number`. The
  wire value is the same number. The SDK does not read `scale` yet.
- **Folds and rule families.** `foldl` with a literal start takes the unit
  its step brings in (`foldl(items, 0, |total, item| total + item.amount)` is
  `Ore`, also when the step adds `item.amount` in one branch of an `if`), and
  is otherwise a plain `Int`; write `Ore(0)` to start from a unit explicitly.
  A rule family may mix literal clauses (`-> 0`) with unit clauses and has the
  unit; such a family, a RuleScope member and a function over a unit are
  generated as Rust over `i64`.

Specified in [Unit types for whole numbers](../rfcs/unit-types.md); reference
in [Unit](../reference/runes.md#unit).

## Constructor names scoped to their type (Experimental)

- **Shared constructor names.** Two sum types in one scope may declare the
  same constructor name, such as `Trade` in `Event` and in `AskYearEvent`. A
  use takes its owner from the type the context expects: a pattern from the
  matched value, an argument, field or result from its declared type, one side
  of `==` from the other side.
- **`Type.Constructor`.** An expression or a pattern can name the owner
  explicitly: `AskYearEvent.Trade(...)`, `| AskYearEvent.Closed -> ...`.
- **No guessing.** A shared name with nothing to give it a type is an error
  that names the owners and the explicit spellings; the owner is never chosen
  by arity or by field names.
- **Data keeps the declared names.** `$variant` in calculation JSON, contracts,
  `runa schema`, displayed values and solver models use the name the
  declaration wrote, and so do generated Rust enums (`AskYearEvent::Trade`).
  The WebAssembly engine runs such models as `runa call` does. Programs
  without shared names are unchanged.

See [the RFC](../rfcs/scoped-constructors.md).

## TypeScript SDK types what it checks (Experimental)

`runa sdk ts` types the partial cases, needs and calls so that what compiles
is what the engine accepts. See
[Calculations](../reference/calculations.md#partial-cases-and-needs).

- **An explicit "none".** In a partial case the answer "none" for an optional
  field is `none` (type `None`, `null` on the wire); a bare `null` is a type
  error and fails validation, so it can no longer be mistaken for, or turn a
  stray `?? null` into, an answer. A field left out or `undefined` stays
  unknown. Complete cases and results keep `T | null`.
- **Unknown variants in switches.** `Unknown<T>` has `$variant?: never`, so an
  exhaustive `switch` on `$variant` over a partial union must handle `{}`.
- **Needs typed by pattern.** Each need carries its `pattern`
  (`openingPositions[].valueOre`); `<Entry>Need` is the union of the needs of
  every pattern, and `<entry>SetAt(case, need, value)` types the value by the
  need's pattern: a need not narrowed to one pattern takes no value. A need's
  `path` is an `InputPath`, made only by the validators, so a negative or
  fractional list index cannot be written.
- **Batched resolvers.** `resolve` calls each resolver once per round with
  all of the round's needs at and below its pattern, the resolvers at the
  same time. A resolver may sit on a field, on a list's elements (`events[]`:
  every field of every event) or on a record (`owner`); each need goes to the
  most specific pattern registered for it, never to two resolvers, so a
  backend answers a round in one call per resolver. A resolver is
  `(needs, context) => (need) => reply`: it fetches for the whole batch and
  returns the function the loop calls for each need, so a reply is made from
  its own need and none is left out. `answer(need, value)` names the need's
  path and types the value by the need's pattern (a resolver of several
  patterns narrows `need.pattern` first); a reply for another path throws
  `ResolveError`, so an answer cannot land in the wrong place, as one from a
  list of answers in another order could. `context.runEntry(need, query,
  case, resolvers)` runs the entry an entry need names.
- **List element keys.** Inside a list whose element type declares a key field,
  a need's `keys` give the element's path, key field and value, typed by the
  contract (`ElementKey<"openingPositions[]", "isin", string>`), for records
  and sum types alike. With batched resolvers this is second-order
  resolution: answer a list with skeletons (key and variant, details left
  out), and the next round's needs ask for only the fields the law reads,
  each with its element's key, which one resolver on the elements fetches in
  one call.
- **Needs and explanations as the engine reports them.** A need's `waiting`
  rules with their sections and paragraphs (each with its act), a `Needs`
  result's `later` needs, and an explanation's `because` contributors and
  `assumptions` are typed and decoded at TypeScript paths.
- **Dates are made, not cast.** `IsoDate` is a branded string: `isoDate(text)`
  (which throws a `RangeError` off the calendar) and the validators make one.
- **Explained calls need an explaining transport.** `EngineTransport` has
  `call` and `callPartial`; `ExplainingTransport` adds `callExplained` and
  `callPartialExplained`, and `<entry>Explained` and `<entry>QueryExplained`
  take it, so a transport that cannot explain is a type error instead of an
  `envelope` error at run time.
- **Lint-clean.** The generated SDK, runtime included, passes typescript-eslint
  `strictTypeChecked` with `--strict --noUncheckedIndexedAccess
  --exactOptionalPropertyTypes`, without disabling a rule.

Compatibility: code written against the earlier 0.4 SDK writes `none` where it
wrote `null` in a partial case, `isoDate("…")` where it wrote a date string,
and `<entry>SetAt(case, need, value)` where it passed a path; resolver maps
are keyed by pattern only, and a resolver `(need, context) => answer(value)`
becomes `(needs, context) => (need) => answer(need, value)`; `<Entry>Resolvers`
is `Resolvers<PartialCase, <Entry>Need, <Entry>InputPatterns>`, and
`context.runEntry` takes the need first (`runEntry(need, query, case,
resolvers)`). `<Entry>InputPaths` is gone
(`<Entry>InputPatterns` remains), and `CalculationEntry` has `patterns`. The
runtime's `unitSchema` takes the unit's name. `runa call` and the
contracts are unchanged, except that a type definition may carry the `key`
its records or variants declare.

## Compatibility

- **Runtime values.** The interpreter's `Value` gains a `Traced` variant; an
  exhaustive `match` on `Value` in Rust code using the library must cover it.
- **TypeScript SDK names.** `<entry>Explained`, `<entry>QueryExplained` and
  the explanation types are generated names; a contract type of the same name
  must be renamed to use the SDK.
- Output without `--explain` is unchanged: `explanation` is left out.
- **Needs.** `waiting_rule`, `section` and `paragraphs` are replaced by
  `waiting: [{rule, section?, paragraphs?: [{paragraph, source?, act?}]}]`;
  needs gain `keys`, the `Needs` result gains `later`, and a date's parts are
  one need at the date's path. An explanation's contributor `paragraphs` are
  objects `{paragraph, source?, act?}` instead of strings, and `cites` gain
  `act`. `runa call --partial` and `--explain` are Experimental.
- **Contracts.** A model with a required `Date` field that has metadata, or
  with an `@ field(key = True)`, gets a new schema fingerprint.
- **TypeScript SDK.** Code written against the 0.3 SDK changes with it: field names are camelCase,
  enum values are strings, dates are ISO strings, need paths are TypeScript
  paths, and `unused_paths`, `attachment_path` and a diagnostic's `case_id`
  are `unusedPaths`, `attachmentPath` and `caseId`. Partial unions use
  `Unknown<T>` for `{}`, and an enum or a
  date has no `Partial` type of its own.
- `runa sdk ts` writes `runtime.ts` next to the entry modules unless
  `--runtime` names another place. A contract type named like a runtime
  export (`Unknown`, `IsoDate`, `Codec`, …) or `<Type>Codec` must be renamed.
- The SDK's changes leave `runa call`, `runa call --partial` and the
  contracts unchanged.
- **Field metadata.** For both metadata forms, `runa check` now rejects a
  provided field whose `subject` is not an input path holding the providing
  entry's input type. Moving metadata onto declarations changes the schema
  fingerprint once (only the provenance differs).
- **Units in the SDK.** TypeScript code that writes a plain number into a
  field whose contract type has a unit must make it with the unit's
  constructor (`ore(1200)`) or take it from another value of that unit.
- **Callback types.** `foldl`'s accumulator now has the type of its start
  value, and a closure bound to a name is checked again at each call with the
  types of its arguments, for every type, not only units. A program whose
  fold step or closure body did not fit those types, which 0.3 accepted
  unchecked, is now a type error.

## Known issues

- Explanations are an interpreter feature; compiled programs do not explain.
- A single value a rule returns unchanged from a deeper rule or the input is
  reported for the outer rule, with the deeper rule or the input in `from`.
