# Futuruna 0.4.0

## Field metadata on declarations (Experimental)

- **`@ field(...)`.** A calculation input field's label, question, help, unit,
  sources and providing entry are written on the field's declaration:
  `# Owner(@ field(label = "Fully tax liable") fully_tax_liable: Bool)`.
  Written before a `#` data type, it describes every input field of that type,
  such as an enum's field or the `$variant` column of a sum with payloads.
  Values are plain strings (`help = "..."`, not `Some("...")`) and no metadata
  record type or `path` is declared.
- **Same contract.** `runa schema` emits the same `field_metadata` entries as
  metadata listed by path; only the provenance (`anchor`, `binding`) names the
  declaration, so the schema fingerprint changes once when a model moves its
  metadata. Workbooks, needs and the TypeScript SDK read it unchanged.
- **One precedence rule.** An exact path for one calculation (anchored field
  records with a string, `pathof` or input-rooted `refof` path) beats a field's
  declaration or `refof(Type::field)` projection, which beats a type's
  default. Two declarations at the winning level are an error naming both.
- **Labels in context.** A label written for a type or its field reads
  `<record field label>: <label>` below a labelled record field, so `Date`'s
  `year` is labelled once and appears as `Trade date: year`. A required record
  field may now be named by exact metadata too, for its label.
- **Diagnostics.** `runa check` reports unknown and repeated keys, a missing
  label, `entry` without `subject`, two `@ field` on one field or type, an
  `@ field` that no field or data type follows, and values that are not
  strings or lists. For both metadata forms, a provided field's `subject` must
  now be an input path holding the providing entry's input type.

Specified in [Field metadata on declarations](../rfcs/field-metadata.md).
