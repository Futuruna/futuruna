# Futuruna 0.5.0

Futuruna 0.5.0 lets a test state an interview in Futuruna. The case is built
with the model's own builders, with `unknown` where a fact is not known yet;
`query entry(case)` asks the calculation about it and answers with the result
or the needs, and `interview` asks round by round until the case is complete.
Under `runa test` every query is also checked against the strict-mode oracle
and the completion test. Named scalar types say once what a kind of value is:
`# Isin: String "International Securities Identification Number" where
isin_shape` is a `String` that passes its checks, and an account id is not
one. A rule family writes its parameter and result types once, on its first
line. Assumptions in every result name their section and their rule apart.
A top-level binding that only metadata reads is compile-time data, so a
metadata role list may mix types; input workbooks tell apart columns that
share a label; and the Danish income-tax examples describe their input
fields with `@ field` on the declarations.

0.5.0 breaks models and readers written for 0.4: `unknown` is a reserved
word, a later clause that repeats its family's types no longer parses, a
local name hides a function of its name, and assumptions and contracts change
shape. `runa fmt --migrate` rewrites most of it; read
[Compatibility](#compatibility) before upgrading. Everything new in this
release is Experimental unless a section says otherwise.

## Needs in the language (Experimental)

```runa
# Spouse(income: Int, cohabiting: Bool)
# Household(income: Int, married: Bool, spouse: Option(Spouse))
# Result(tax: Int)

@ section transfer {
| threshold(h: Household) -> match h.spouse {
    | Some(s) -> if s.cohabiting { 200 - s.income } else { 100 }
    | None -> 100
}
}

@ calculate
| household_tax(h: Household) -> Result(tax = h.income - threshold(h))

= with_spouse = Household(income = 500, married = True, spouse = Some(Spouse(income = 50, cohabiting = True)))
= first = query household_tax(Household(income = 500, married = True, spouse = unknown))
= asked = interview(|c| query household_tax(c), Household(income = 500, married = True, spouse = unknown), with_spouse)

@ print(match first { | Needs -> map(first.needs, |n| n.path) == [pathof(Household::spouse)] | Complete -> False }) -- True
@ print(asked.rounds == [[pathof(Household::spouse)], [pathof(Household::spouse::cohabiting), pathof(Household::spouse::income)]]) -- True
@ print(asked.result == household_tax(with_spouse)) -- True
```

- **`unknown`** is a value not known yet. It means what a left-out field
  means in a partial JSON case: for an optional, a scalar or a list it is one
  unknown; for a record, the record exists with each field unknown; for a sum
  type, the variant is unknown. `Some(unknown)` of a record says "present,
  nothing known yet". It takes the type of its place, as a number literal
  takes its unit: an argument, a field value, a list element, a typed
  binding, a declared result or a branch. Reading it is a check error: as an
  operand, a side of a comparison, a scrutinee, a condition, the argument of
  a builtin such as `show`, or the value of an untyped binding. A builder
  that reads an `unknown` before a query stops with an error naming the
  `unknown`'s line.
- **`query entry(case)`** asks a calculation entry (`@ calculate`, declared in
  the asking file or a file it imports) about a case, as `runa call --partial`
  does on the entry's own checked program. It returns
  `Query(o, i) = Complete(result: o, unused: List(Path(i)), assumptions:
  List(QueryAssumption)) | Needs(needs: List(Need(i)))`. `query` is a keyword
  only in `query name(...)`; elsewhere it stays a name.
- **Assumptions by checked name.** A `QueryAssumption` has `section`, `rule`
  and `binding`, each an `Option(ProgramReference)`, so a test states which
  assumption a case rests on with `refof(...)`:
  `any(q.assumptions, |a| a.binding == Some(refof(assumption_closing_day)))`.
- **`Need(i)`** has the members of a need in the partial result: `kind`
  (`FactNeed` or `EntryNeed`), `path: Path(i)`, `keys`, `entry`, `subject`,
  `label`, `question`, `help`, `unit`, `sources` and `waiting`. A waiting
  rule's `section` is a `ProgramSectionReference`, compared with
  `Some(refof(section transfer))`.
- **Typed paths.** `Path(i)` is a path into a value of type `i`.
  `pathof(T::...)` is a `Path(T)` where a path is expected and a `String`
  elsewhere, as before. It takes list indices
  (`pathof(TaxCase::accounts[1]::closing_cash_ore)`) and names the alternative
  of a sum type it passes through
  (`taxpayer.outside_endavu.OutsideDeclared.other_share_income_ore`), as field
  metadata does. Comparing paths of different root types is a check error.
- **`fill(partial, complete, paths)`** writes into `partial`, at each path,
  the value of `complete` there: a record as existing with its fields
  unknown, a variant by its tag, every other value (a `Date` too) whole.
  **`interview(ask, partial, complete)`** asks, fills each round's needs from
  `complete` and asks again until the answer is `Complete`; it returns
  `Interview(rounds: List(List(Path(i))), result: o)`.
- **Tests run the guarantee.** Outside tests a query only propagates. Under
  `runa test` every query also runs the strict-mode oracle and the completion
  test; a violation fails the test at the query, as
  `file:line: query entry, round N: ...`, naming the completion that disproves
  it.
- **No calculation reaches a query.** `runa check` reports a `query` or
  `unknown` that any `@ calculate` entry can reach, with the call chain.
- **Interpreter only.** `runa build` and `runa run` refuse a program with a
  `query` or `unknown`, naming each; `runa check` checks its frontend and
  reports `interpreted (query)`, and `runa test --run` runs such a test in the
  interpreter and marks it `interpreted (query)`.
- **Sections across files.** `refof(section name)` names a section of the
  file it stands in or of a file it imports; a name two of those files
  declare is a check error naming both.
- **Typed entry metadata.** A field another calculation provides writes
  `entry = refof(share_income)` and
  `subject = pathof(TaxCase::taxpayer::spouse)` (in a field record,
  `entry: ProgramReference?`). `runa check` reports, naming the field, an
  `entry` that is not an `@ calculate` entry, a subject rooted at another type
  than the calculation's input or holding another type than the entry takes,
  and a field whose type is not the entry's result type. The contract carries
  the same strings as before (`"entry": "share_income"`,
  `"subject": "taxpayer.spouse"`). The string forms are still read, with the
  same checks.

Reference: [Needs in the language](../reference/calculations.md#needs-in-the-language);
design: [Needs in the language](../rfcs/needs-in-the-language.md).

## Assumptions name their section and rule

Each assumption of a result names the law section it is written in
(`section`) and the rule, member or function it is written on (`rule`), each
left out when it does not apply, beside its `binding` and `value`, in
`runa call`, `runa call --partial`, the result workbook and the TypeScript SDK:

```json
{ "section": "closing", "binding": "closing_day",
  "value": { "id": "CLOSING-DAY", "statement": "The value on the closing day is the custodian's." } }
```

In 0.4.1 one `section` string held the section or, outside any section, the
rule's name, so a reader could not tell which.

## Workbook columns that share a label are told apart

- **The bug.** An input workbook heads each column with its field's label,
  so a labelled type held at two paths of one sheet gave both columns one
  header. With the labels on the Danish declarations as first written (see
  [below](#the-danish-examples-describe-their-fields-on-the-declarations)),
  the Personskat property sheet headed three columns `Årets honorarbrug`, one
  per property type, where before they showed their humanized paths. In the
  Personskat workbook 48 of 1,861 sheets had shared headers (42 before the
  migration: `cases` already headed the taxpayer's and the spouse's salary
  alike).
- **The fix.** Columns of one sheet that share a label are each qualified by
  the humanized ancestors where their paths part (`Ægtefælle / Skatteår`).
  A column with no such ancestor keeps the bare label; columns the
  ancestors cannot tell apart add their canonical path. A label no other
  column of the sheet carries is unchanged. Reading still maps columns by
  position, and a workbook written with the bare shared labels still reads.

## Bindings named like a function or rule

- A top-level binding may take the name of a rule or a function
  (`= tax = tax(case)`): `tax` reads the binding and `tax(...)` calls the rule
  or function, unless the binding holds a function, which then takes the
  calls after it. For a function this is new: before, `runa check` passed and
  the interpreter called the binding's value and stopped with "value is not
  callable". Each such binding gets a warning naming the binding, the
  function or rule and where it is declared, and what each use means; a
  warning does not fail the command. Native code agrees: a call `tax(...)`
  inside a function body, where `runa build` had emitted a call of the
  binding's value and the generated Rust did not compile, calls the rule or
  function.
- A parameter, lambda parameter, match pattern, block binding or field of a
  rule scope (`# Case(income: Int) { … }`) hides a function or rule of its
  name in its scope. Calling one that holds no function is a check error
  naming the hidden function. A rule of the scope itself may share a field's
  name: `income()` calls the rule and `income` reads the field.

## A binding only metadata reads is compile-time data

- **The bug.** `= kilder = [Source(value = law), Guidance(value = note)]`,
  with `law` and `note` of different types and read only by
  `@ field(sources = kilder)`, passed `runa check --frontend`, but the
  generated Rust did not compile (`mismatched types` in a `Vec`). The same
  list written inline in `@ field` compiled. Only a program that declared a
  calculation left such a binding out of the Rust, and only for `@ meta`.
- **The fix.** A top-level binding that `@ meta`, `@ section` or `@ field`
  values resolve to ground data, in the root file or a file it imports
  plainly or qualified (`@ import Roles from ./roles`), and that no runtime
  code reads is compile-time data in every program: native code, libraries
  (`runa --emit lib`) and WebAssembly (`runa wasm`) neither emit nor
  initialize it, and a library exports no getter for it. A metadata role list
  is erased, each role value keeping its own type, so its values may have
  different types, written inline or in such a binding.
- **A runtime list holds one type.** A list whose elements have types that
  do not join is a check error, also for constructor values of one generic
  type with different type arguments (`Role(Law)` and `Role(Note)`): Futuruna
  has no runtime type for a list of both. In a top-level binding runtime code
  reads, the error names the binding: ``list elements must have the same
  type; first element is `Role(Law)` but this element is `Role(Note)`.
  `kilder` is runtime data, …``. Before, a list of values whose types were
  not literals passed the check and failed in the generated Rust.

## Named scalar types (Experimental)

```runa
| isin_shape(text: String) -> string_length(text) == 12
@ field(label = "ISIN")
# Isin: String "International Securities Identification Number" where isin_shape
# AccountId: String "the custodian's identifier of an account"
# Month: Int "a month of the year" where between(1, 12)
| between(n: Int, low: Int, high: Int) -> n >= low && n <= high
```

A named scalar is a `String` or `Int` whose values pass every check after
`where`, in order; `between(1, 12)` checks `between(value, 1, 12)`. A named
scalar without `where` is a name and nothing more.

- **An account id is not an ISIN.** An `Isin` is accepted where a `String` is
  expected, also inside `List`, `Set`, `Option` and `Map`. A plain `String`
  or an `AccountId` where an `Isin` is expected is a type error, and so is
  `map_contains(accounts, e.isin)` when `accounts` is keyed by `AccountId`.
  Any operator other than a comparison works on the primitive and gives the
  primitive, so `p.account_id + "/" + p.isin` is a `String`.
- **Values are checked where they are made.** `runa check` runs the checks on
  a literal that takes a named scalar (`= home: Isin = "DK006053491"` is an
  error). `Isin(p)` stops on a value that fails a check; `parse(Isin, p)`
  gives `Result(Isin, String)`, whose `Err` names the false check.
  `String(isin)` and `Int(id)` take the name off. A check always runs the
  definition its name has in the file that declares the type.
- **Inputs are checked.** `runa call` (also `--partial`) and
  `runa template --input` run the checks on every input value of a named
  scalar type and report a failure as an input diagnostic at its path, with
  the members `scalar` and `check`.
- **Field metadata once.** `@ field(...)` before the declaration labels every
  input field that holds the type. A field's `@ field` that repeats it is an
  error; `@ field(key = True)` on the field marks a key and keeps the type's
  label.
- **Contract and SDK.** `runa schema` marks a type reference
  `"scalar": "Isin"` and lists the named scalars with their descriptions and
  checks. `runa sdk ts` declares
  `type Isin = string & { readonly __scalar: "Isin" }`, `IsinSchema` and the
  constructor `isin(text)`, and throws `CalculationError` of kind `input`
  with `scalar` and `check` when the engine refuses a value.
- **Erased elsewhere.** At runtime, on the wire and in generated Rust
  (`pub type Isin = String;`) a value is its primitive.
- **Proofs use the checks.** `runa verify` assumes each check of a named
  scalar input that translates to SMT, and a counterexample names a check it
  could not assume. `Isin(p)` in a verified body is an obligation that the
  checks hold for `p`; where a check does not translate, the claim is
  unsupported, never proved.

Reference: [Named scalar](../reference/runes.md#named-scalar) and
[Named scalar types](../reference/calculations.md#named-scalar-types); design:
[Named scalar types and rule result types](../rfcs/named-scalar-types-and-rule-result-types.md).

## Declared rule result types (Experimental)

A rule family writes its types once, on its first line:

```runa
| days_in_month(year: Int, month: Int): Int -> 31
| days_in_month(year, month) -> 30 under month == 4 || month == 6 || month == 9 || month == 11

| fib(n: Int): Int
| fib(0) -> 0
| fib(1) -> 1
| fib(n) -> fib(n - 1) + fib(n - 2)
```

- `: R` after the declaring line's parameters declares the family's result
  type. A line with `: R` and no `->` declares a family whose first clause
  matches a pattern; `@ cite` may not stand above it. A family without `: R`
  is inferred as before.
- Every later clause and every exception writes a name or a pattern at each
  position; an exception over a family imported from another module takes
  that module's parameter types. A type on a later clause or an exception, a
  later name that differs from the declaring line's, a second declaration and
  a declaration without a clause are errors that name the declaring line. A
  name repeated in one head (`| pairing(a, a)`) is a pattern that requires
  equal arguments.
- Each clause is checked against `R`: a number takes `R`'s unit
  (`| loss(): Ore -> 0`), `None`, `[]` and a shared constructor take their
  type from `R`, a fact or goal body requires `R = Bool`, and a clause of
  another type is an error at that clause.
- A family declared `: Bool` answers `False` when no clause applies; a family
  of any other declared type stops with `no value rule matched`.
- Proofs, generated Rust and explanations read the same rules as before.

Reference: [Declared result types](../reference/runes.md#declared-result-types-experimental).

## The Danish examples describe their fields on the declarations

- **Before.** `examples/danish-income-tax` described input fields with its
  own records (`Beregningsfelt(path: Tekst, …)` and four related types),
  3,197 of them, each naming its field by a string path. A path with a typo
  was silently wrong.
- **Now.** 1,884 `@ field` declarations carry the label, question, help,
  unit and sources on the field itself, checked by `runa check` and carried
  by `runa schema`, `runa template`, needs and the SDK. 1,309 records stay
  where the text depends on where the type is used (date parts, own or
  spouse's facts, report rows), now one record type naming its field with
  `refof` instead of a string. Shared source lists are written once (214),
  and each law source lives in the law module that cites it.
- **What a reader sees.** Across the 19 calculation entries, no path lost or
  changed a label, question, help or unit. 15,214 paths gained metadata,
  almost all where personskat is embedded in grøn check and the § 14
  part-year calculation; none of the gained text speaks from another
  person's perspective. AMBL § 4 is now one source binding, so 1,056 paths
  show the law module's retrieval date (2026-08-11) instead of a duplicate's.
- **Text written for one use stays at that use.** Text on a declaration
  shows wherever the type is used, so text written for one context stays on
  records for that context: the fee (honorar) depreciation route's AL § 5 and
  § 11 fields (not business depreciation or property-sale installations),
  the departure-share acquisition date (not a generic ABL date), the
  minimum-certificate institute (not ordinary shares) and the § 40 C lot
  identification. 2,600 paths no longer show text that did not hold there.
  The two stand-alone investment-classification entries show the
  classification year without the help that points to a personskat tax year.
- **Lines.** The examples grew from 165,036 to 168,226 lines: the
  declarations name more than the records did, and `@ field` is written over
  several lines.

## Compatibility

### Models

- **`unknown` is reserved.** A binding, parameter or function named
  `unknown` is a parse error; `runa fmt --migrate` renames it to `unknown_`.
  `query` before `name(` starts a query; a name `query` elsewhere is
  unaffected.
- **Rule types are written once.** A later clause or exception that repeats
  its family's parameter types no longer parses, and in a family that
  declares a type, a later clause that names a parameter differently is an
  error. `runa fmt --migrate` writes each family's types once, declares its
  result type where that changes nothing, and lists the families it could not
  declare or rewrite, with the reason.
- **Local names hide functions.** A parameter, lambda parameter, match
  pattern, block binding or rule-scope field named like a function or rule
  hides it in its scope; a call of one that holds no function is a check
  error.
- **Named scalar metadata.** A field's `@ field` that repeats its named
  scalar type's is an error; `runa fmt --migrate` removes it.
- **Typed entry metadata.** `runa fmt --migrate` rewrites string `entry` and
  `subject` field metadata as `refof`/`pathof` when exactly one calculation
  input reaches the field, and lists the others as `file:line` with the
  reason. The string forms still check.
- **Lists hold one type.** A list literal whose elements have known types
  that do not join (two record types, or one generic type with different
  type arguments) now fails `runa check` outside metadata. It failed to
  compile before.

### Output and contracts

- **Assumptions.** Each assumption in `runa call`, `runa call --partial`, the
  result workbook and the TypeScript SDK is
  `{section?, rule?, binding?, value}`: `section` is the law section only, and
  the rule it is written on moves to `rule`. A reader of 0.4.1's `section`
  must read both.
- **Contract hashes.** A model whose fields or results use a named scalar
  type gets a new schema hash: type references gain `scalar` and the contract
  gains `scalars`. A model without named scalars keeps its contract.
- **Input diagnostics.** A value refused by a named scalar check is an input
  diagnostic with the members `scalar` and `check`, present only where a
  program declares a named scalar.
- **Workbook headers.** Input workbook headers that columns of one sheet
  shared are qualified. A tool that finds a column by its visible header must
  use the new header, or the canonical path in the hidden `_columns` sheet.

### Generated code

- A library or WebAssembly module no longer exports a getter for a top-level
  binding only metadata reads.
- `runa --emit lib` type-checks the program first, as `--emit rust` does: a
  program that fails `runa check` emits no library.

## Known issues

- `runa verify` treats only variables passed directly as named-scalar inputs:
  it does not assume the checks of a named scalar field of a record input.
- An invariant over a free variable of a named scalar type over `String` is
  reported unsupported.
- The [known issues of 0.4.2](0.4.2.md#known-issues) remain.
