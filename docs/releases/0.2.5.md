# Futuruna 0.2.5

Futuruna 0.2.5 keeps an `http_serve` server running when one request fails,
lets `runa verify` prove claims about ordinary programs, makes `runa test`
type-check each file before running it, and fixes the defects an independent
review found in 0.2.4.

## HTTP server

- **One bad request never stops the server.** Each handler call runs on a
  blocking worker thread. A handler that fails at runtime, for example on a
  checked integer overflow, answers `500` with `{"error":"internal error"}`
  and reports `error: request <METHOD> <path>: <message>` on stderr; the
  process keeps serving. In 0.2.4 the process exited and later requests were
  refused. Outside a handler a runtime error still ends the program with
  status 1.
- **Request bodies.** A body larger than 1 MiB answers `413` and a body that
  is not valid UTF-8 answers `400`; the handler is not called. In 0.2.4 an
  oversized body reached the handler as an empty string and invalid UTF-8 was
  replaced silently. A handler result with an invalid status or content type
  answers `500`. All these error responses are `application/json`.
- **Handlers bound to a name.** `= handler = |path, method, body| ...` followed
  by `@ http_serve(port, handler)` compiles and the handler may read top-level
  bindings. 0.2.4 said "a handler, written as a closure or named as a function"
  may read them; a closure bound to a top-level name still failed to compile.

## Verification

- **`runa verify` runs the `runa check` frontend first,** with the same
  prelude and imports. `clamp`, `min_int`, `max_int` and the `Meta` and
  `MetaRole` marker traits were unknown to verify in 0.2.4.
- **Rules with Int arithmetic translate.** The solver proves that no
  reachable `+`, `-`, `*`, `/` or `%` overflows or divides by zero, so a rule
  doing arithmetic is proved or refuted with an overflowing input instead of
  being rejected as not total. The documented `TaxCase.tax_due()` example did
  not verify in 0.2.4; it does now.
- **`max_int`, `min_int`, `clamp` and `abs` on Int translate exactly**;
  `abs` of the minimum Int is an overflow, as it is at runtime.
- **Unsupported claims are reported one by one.** The summary counts them
  (`Verification: 4 of 6 invariant(s) proved, 2 unsupported.`), and
  `runa verify --allow-unsupported` exits 0 when at least one claim is proved
  and every other claim is one the SMT layer cannot translate. A refuted
  claim, an unknown result or a missing solver still exits 1.
- The reference now states that a file without invariants exits 0.

## Testing

- **`runa test` type-checks each file before running it**, like `runa FILE`.
  A type error is a FAIL with its diagnostic; in 0.2.4 the file was run
  anyway and could stop with an internal panic.

## Corrections to 0.2.4

0.2.4 claimed more than it delivered in four places. Each case compiled to
Rust that rustc rejected ("Futuruna compiler bug"); 0.2.5 fixes them:

- **Omitted result types ending in a builtin call.** 0.2.4 said a function
  whose result cannot be inferred gets a located error. A body ending in
  `char_at`, `zip`, `enumerate`, `flat_map`, `random_float()` or `head` on a
  generic list got neither. Such a call now counts as a value: `char_at`,
  `zip`, `enumerate` and `random_float` results are inferred, and any result
  still unknown is the located error.
- **`random_float` in rules.** It was listed with one argument instead of
  none, so a rule ending in `random_float()` could not be compiled.
- **Qualified imports.** Functions of `@ import U from ./utils` that omit
  their result type were neither inferred nor reported. They are now inferred
  within their module, or reported with a located error in that module.
- **`http_serve` handlers bound to a top-level name** (see above).

## Language

- `Tuple` is the built-in tuple type and can no longer name a user type; a
  user type named `Tuple` made every `(A, B)` annotation fail to compile.
- `Tuple(Int)` is again reported as an unknown type, as in 0.2.3.
- A tuple type accepts a trailing comma, `(Int, String,)`, like a tuple
  literal.

## Interpreter and compiled code agree

- `fst`, `snd` and `trd` on a `Pair` (or another constructor) return its
  fields in the interpreter, as in compiled code; they returned `()`.
- `filter` on a `Set` returns the matching elements as a `List` in value
  order in the interpreter, as in compiled code; it returned `[]`.

## Known issues

- An omitted result type is not checked against a declared binding type:
  `= q: Int = f()` where `f` returns `String` is accepted by the checker.
- A closure passed for a tuple-typed parameter, such as `k(|p| p)` for
  `((Int, Int)) -> (Int, Int)`, does not compile to native code.
- `http_serve` called inside a `>` function does not compile; call it at the
  top level.

## Installation

Use the checksummed binaries on the
[GitHub release](https://github.com/Futuruna/futuruna/releases/tag/v0.2.5), or
build the tag with
`cargo install --git https://github.com/Futuruna/futuruna --tag v0.2.5 --locked futuruna`.
