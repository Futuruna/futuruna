# Futuruna 0.7.0

Futuruna 0.7.0 adds **open keyed inputs**: the law asks for an entry whose key
it computes ("the account's balance on 20 February the year after"), and the
integrator gives the entries asked for, without guessing which keys to supply.
Everything new in this release is Experimental.

## Open collections (Experimental)

```runa
# Balance(@ field(key = True, label = "Day") day: String, @ field(label = "Value") value: Int)
# Account(delisted: String, @ field(label = "Balance", open = True) balances: List(Balance))

@ entry
> deemed(a: Account) -> Int {
    lookup(a.balances, a.delisted).value
}
```

- **`@ field(open = True)`** on a field of type `List(T)`, where `T` declares a
  key field (`@ field(key = True)`): the case never gives the collection whole.
  It may be left out (no entries given yet). `runa check` reports `open` on a
  type, on a field that is not a `List`, or of a type without a key field.
- **`lookup(list, key)`** is the entry whose key field is `key`: on an open
  field (written `lookup(record.field, key)`) the entry itself, on any other
  keyed list `Some(entry)` or `None`. Its key has the key field's type.
- **An entry the case does not give** is, in a partial case, a need at
  `balances[day="2027-02-20"]` (the key as JSON) with that key in `keys` and
  the field's metadata, answered with the whole entry; a complete call fails
  with an error naming the field and the key. A missing entry is fallible, so a
  partial case never completes past it.
- **No whole-collection reads.** Every read of an open field other than as
  `lookup`'s collection (`filter`, `map`, a loop, passing it on) is a check
  error: the case never holds all of it.
- **`fill`, `answer`, `from_case`** write an entry need by adding the entry.
- **TypeScript SDK.** The need's pattern is `balances[]`, its answer the
  element type: `given(need, { day, value })` adds the entry, and `setAt` sets
  the key from the path or refuses another. `[]` in a pattern stands for a
  list index or an entry key. The open field is optional in the input type and
  `balances` is no pattern.
- **Interpreter only.** `lookup` runs in the interpreter, as `query` does;
  `runa build` and `runa run` refuse it.

See [Open collections](../reference/calculations.md#open-collections) and the
RFC [Open keyed inputs](../rfcs/open-keyed-inputs.md).

## Descriptive text on request (Experimental)

A result carries what the caller acts on; the law's text (a need's label,
question, help, unit and sources, an assumption's statement and
`resolve_with`) comes only when asked, as explanations do with `--explain`.
See [Partial cases](../reference/calculations.md) and Compatibility below.

## Law idioms

- **Dates are ordered.** `<`, `<=`, `>`, `>=` compare two `Date`s
  chronologically in the checker, the interpreter, generated Rust and the SMT
  encoding of `runa verify` and `runa audit`; a partial case reads a comparison
  of an unknown date as unknown. `<` on any other declared type is now a type
  error (it failed in the interpreter). See
  [Comparison](../reference/basics.md#comparison).
- **Option guards are audited.** `runa verify` and `runa audit` read an
  `Option` of any payload (`closed: Date?`) through `is_some`, `is_none`,
  `unwrap_or` and a `match` on `Some`/`None`: a generic function's call is
  translated as its body at the argument's type (before, at `Int` only, so a
  `Date?` guard was "not analyzed"). See
  [runa verify](../reference/runes.md).
- **Tuple patterns.** `match (lost_right, closed) { | (Some(l), None) -> … }`
  matches two values together, in the interpreter and native code; the arms
  are checked for exhaustiveness together, and `runa verify` and `runa audit`
  translate a match on a tuple written in place element by element. See
  [match](../reference/basics.md#match).
- **Constructor patterns in rule heads.** A family whose clause heads cover
  every variant (`| due(y, ChangedBySkat(d)) -> … | due(y, CorrectedByInstitute(r)) -> …`)
  is total: it compiles natively without a fallback clause, and `runa verify`
  and `runa audit` read it as never missing. See
  [Declared result types](../reference/runes.md#declared-result-types-experimental).

## Compatibility

- **The default output is leaner.** A need carries `kind`, `path`, `pattern`
  (SDK), `keys`, `waiting` (each rule's name and section) and, for an entry
  need, `entry` and `subject`; no `label`, `question`, `help`, `unit`,
  `sources` or cited `paragraphs`. An assumption's value leaves out
  `statement` and `resolve_with`. Ask for text with `runa call --describe`
  (all) or `--describe=label,question,...`, with `"describe": [...]` in the
  input document (the WebAssembly engine), or with
  `options.describe: { needs: [...], assumptions: [...] }` on an SDK call,
  query or answer. Needs in the language (`query`, `answer`) keep their text.
- `lookup` is a builtin: a program that declares its own `lookup` keeps it.
- A type with an open field has a new content hash; other hashes and schema
  fingerprints are unchanged (`open` is written only when true).
- The `@ field` label rule now reads "a `label`, or only the markers `key` and
  `open`".
- Need paths may hold `[field=value]` steps; a client that parses paths must
  read them (the runtime's `parsePath`, `pathPattern` and
  `matchesPathPattern` do).
- Removed `answer_guide(entry)` with `AnswerGuide`/`GuideNeed`, and the SDK's
  `<entry>Guide` with the runtime's `AnswerGuide`/`GuideNeed`: no consumer;
  every need carries its label, question and help, and the typed `Need` union
  keeps `resolve` exhaustive.
- Removed `context.runEntry`, `AnswerOptions` (`frames`), `pending`,
  `PendingEntry` and `AnswerCycleError` from the TypeScript runtime and SDK:
  no consumer; an entry need is answered by `resolve` like any other.
- Removed the SDK's explained calls (`<entry>Explained`,
  `<entry>QueryExplained`), `ExplainingTransport` and the explanation types:
  no consumer; auditing is `runa call --explain`.

## Known limitations

- An open collection has no answer "there is no entry"; model a day without a
  balance as an entry.
- A whole-record read (`show(case)`, `case == other`, a record pattern) still
  reads an open field as the case gives it.
- `pathof` cannot name an entry by key; tests compare entry needs by `keys`.
