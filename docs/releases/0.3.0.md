# Futuruna 0.3.0

Futuruna 0.3.0 lets a calculation answer a case that leaves facts out: it
returns the result when the given facts decide it, or the facts it still
needs, each with its question, help, unit, sources and the rule waiting for
it. The interpreter also runs in WebAssembly, so a Node host can call a model
without a `runa` binary, and `runa sdk ts` generates a typed TypeScript client
for a model's calculations. `runa audit` and `runa verify` report the inputs
no clause of a rule covers. Everything new in this release is Experimental.

## Partial cases and needs (Experimental)

- **`runa call --partial`.** A case may leave fields out. Each case answers
  `Complete` with its result and the provided input paths evaluation never
  read (`unused_paths`), or `Needs` with every fact and entry that blocks the
  result. A client writes answers into the same case at the needs' paths and
  calls again; the engine keeps no state between rounds. The output envelope
  is `futuruna.calculate.partial-output.v1`, and
  `runa schema --format partial-result` prints its JSON Schema.
- **Four kinds of input.** A value is the answer, `{}` for a record means the
  record exists with its fields unknown, `null` for an optional field means
  "none", and a field left out is unknown. A sum type without `$variant` is
  unknown at `path.$variant`.
- **Decided where the known facts decide.** `False && unknown` is `False`; an
  `if`, a `match` or a rule whose possible outcomes agree is decided; a clause
  with an unknown guard blocks the clauses below it. Builtins read only what
  they need (`length` needs the list, not its elements). Speculation under an
  unknown condition is bounded per case, and a recursive call under an
  unknown condition is not explored, so every partial case terminates.
- **Callback results stay unknown.** When a function passed to `map`,
  `flat_map`, `foldl` or another higher-order builtin returns an unknown
  value, the builtin's result is unknown; an unknown list is never read as
  empty. Destructuring an unknown value binds unknown parts, and a loop over
  an unknown list or condition stops the case with its needs. A validation
  issue that depends on an unknown fact therefore keeps the case at `Needs`.
- **Entry needs.** Field metadata can say that another calculation entry
  provides a field for a subject (`entry`, `subject`). Such a field's need
  has kind `entry`. `runa check` requires the field to have that entry's
  result type.
- **The guarantee and its checks.** If a partial case returns `Complete(r)`,
  every completion of its unknown fields returns `r` or stops with an
  arithmetic-overflow error. `runa call --partial=strict` stops at the first
  unknown read and is the test oracle; `runa call --partial=check` runs the
  oracle and the completion test (generated completions must return `r`) and
  reports every violation as a diagnostic.
- **Leave-one-out check.** `scripts/partial-leave-one-out.py` leaves out each
  input leaf of a case, and each whole list, and runs every resulting case
  with `--partial=check`.
- **Interpreter only.** Partial cases are JSON and run in the interpreter;
  `--partial` is refused outside `runa call`.

Without `--partial` nothing changes. Specified in
[Calculation needs](../rfcs/calculation-needs.md).

## Field metadata on optional members (Experimental)

- Members of optional records and sums, at any depth, take calculation field
  metadata: exact paths, `pathof` through the optional, and `refof`
  projection, with the existing precedence and duplicate rules. Needs on
  paths such as `taxpayer.spouse.*` carry their question, help and sources.
  A path into an undeclared member is still an error.
- Workbooks keep an optional composite in one JSON cell. Its header note lists
  each member's label and question, and the `_columns` sheet records the
  members' metadata in `member` rows after the column rows.

## TypeScript SDK (Experimental)

`runa sdk ts model.calculate.runa --out sdk/` generates ES modules from the
calculation contracts of one file: types with field TSDoc, Zod validators and
`SCHEMA_HASH` per entry, partial-case types with needs typed by input path,
`setAt`, a call and a query function per entry over an `EngineTransport`, and
a `resolve` loop that hands each need to the resolver registered for its path
pattern. A contract type named like a generated name (`Need`, `Complete`,
`Needs`, `Partial`, `Schema` and entry-derived names) is an error; rename the
type. See [Calculations](../reference/calculations.md#typescript-sdk).

## The interpreter in WebAssembly (Experimental)

- `research/wasm-engine` builds the interpreter for `wasm32-unknown-unknown`.
  `new Model(sources, main)` parses and type-checks a model from its source
  files; `Model.call(entry, input)` returns the `runa call` output document and
  `Model.callPartial(entry, input)` the `runa call --partial` document.
- A `Model` prepares each entry on its first call (60–100 ms on the tax
  engine in Node) and keeps it: later calls run only their cases, each from
  the same isolated starting state. One Aktiesparekonto case then takes about
  3.4 ms, and the tax report's demo case 15 ms.
- A host can register source files by path; imports, type checking and
  calculation calls read a registered file before the filesystem.
- Calculation calls read the clock only when tracing, so they run where no
  clock is available.

[WebAssembly engine for D1](../rfcs/wasm-engine-d1.md) compares the compiled
model with the interpreter on the tax engine and recommends the interpreter.

## Calculation cases

- **Prepared once.** A call prepares its entry (rule-dispatch metadata and
  the initialized program) once for all its cases; `runa call --partial=check`
  shares one preparation between its propagating, strict and completion runs.
- **Isolation of actors and subjects.** A case that sent to an actor or
  emitted on a subject the model holds at the top level changed it for the
  later cases of the same batch. The program is now initialized again before
  the next case, so every case starts from the initialized program alone, and a
  case's named-scope subscriptions end with the case.

## Compiling to WebAssembly and native code

- **Generic top-level bindings.** A top-level binding holding a constructor of
  a generic type, such as `Metadata(attachments = (Source(...), ...))`, is
  declared with its type arguments; rustc rejected it before. This fixes
  `runa wasm`, `runa lib` and `runa build` of programs that read such a
  binding.
- **String parameters in WASM.** A function with a read-only `String`
  parameter that compared it with a literal did not compile in WASM mode. A
  WASM export takes a JavaScript string and works on its own copy.
- **`runa wasm` type-checks** before generating code, as `runa build` does.
- **`runa wasm --target nodejs|web|bundler`** selects the package kind:
  `web` (the default) is an ES module for the browser, `nodejs` a CommonJS
  package Node loads already initialized, `bundler` an ES module for bundlers.

## Rule gaps in `runa audit` and `runa verify` (Experimental)

- With Z3, `runa audit` checks every partial value rule family in scope for a
  gap: an input on which no clause applies, so a
  call would stop with "no value rule matched". A gap is reported with the
  family's clauses in dispatch order and a witness naming each argument and
  each RuleScope field (`self.<field>`). Families with an unconditional
  clause, and Boolean families (which answer `False` on a miss), are not
  checked; a family with a guard the solver cannot translate is listed under
  "gaps not checked".
- JSON: `clause_reachability.findings[]` gains `kind: "gap"` with `clauses`
  and `witness`; `summary` gains `gaps` and `gap_not_checked`; a top-level
  `gap_not_checked` list gives each unchecked family with its reason.
- Audit findings stay informational (exit 0). `runa verify` already failed a
  claim that reaches a partial family; the skipped claim now names the input
  the family leaves uncovered. A RuleScope member is named with its scope
  (`Share.tax`, not `tax`), so the claim reports only its own family's gap,
  not those of other families with the same member name.
- **Scope.** Auditing a calculation file covers every rule family its entry
  reaches, including families in imported files; every other file covers the
  families with a clause in it. The report states its scope and how many
  families and clauses it analysed, and says so when nothing was in scope.
  JSON gains `clause_reachability.scope`, `families` (each with its files),
  `summary.files` and a `file` on every finding.
- **JSON for every file.** `runa audit <file> --json` works on files without
  a calculation too: the entry sections are `null`, and every report carries
  a `topology` object with the structural audit (rules, invariants,
  contradictions, tensions, asymmetries, invariant gaps).

## Compatibility

- **Schema hashes.** A contract whose field metadata targets members of
  optional composites gets a new schema hash. Contracts without such metadata
  keep theirs, except where `refof` now projects into an optional: the tax
  engine's `personskat` contract has a new hash. Regenerate templates and
  clients from those contracts.
- **Audit JSON.** An overlap witness for a RuleScope rule names each field
  (`"self.own_ore": "-1"`) instead of one `self` value
  (`"self": "(ShareTax (- 1) 1 true)"`), and findings, `summary` and the top level
  gain the gap fields above. A consumer of the audit JSON must accept the new
  shape; `runa audit` is Experimental.
- **TypeScript SDK names.** A model whose contract type collides with a name
  `runa sdk ts` generates must rename the type to use the SDK; other commands
  are unaffected.
- **Rust library.** `calculate::invoke_calculation_cases`,
  `invoke_partial_calculation_cases` and `check_partial_calculation_cases` are
  replaced by `calculate::PreparedCalculation`: `new` with the contract,
  statements and source directory, then `invoke`, `invoke_partial` or
  `check_partial` as often as needed.
