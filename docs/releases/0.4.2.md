# Futuruna 0.4.2

Futuruna 0.4.2 fixes two ways a program could give a wrong answer without an
error, and nine places where a reader or writer could not rely on what they
read. `round(pow(10.0, 300.0))` returned `9223372036854775807`: a Float
outside the `Int` range became the largest `Int`. It is now an error that names
the value. An imported file's own call of a function reached a function of the
same name in the file importing it; it now reaches the imported file's own, so
what a law module computes no longer depends on who imports it. A name now
means what its nearest declaration says, in the checker,
the interpreter and compiled code alike: a local named `ask`, an imported
function named `first`, a parameter called as a function, two top-level
bindings of one name, and a rule and a function of one name, also in two
files. A bare
`print(...)` in a function body is an error that asks for `@ print(...)`, as
at top level.

0.4.2 rejects programs that 0.4.1 accepted; see
[Compatibility](#compatibility).

## `round` and `floor` never saturate

- **The bug.** `round` and `floor` of a Float outside the `Int` range gave the
  nearest `Int` (`9223372036854775807` for `round(pow(10.0, 300.0))`), and of
  NaN gave `0`, in the interpreter, in the interpreter compiled to WebAssembly
  and in compiled code. No error was reported.
- **The fix.** Both stop with a runtime error that names the value, in every
  mode with the same text: `round: 1e300 does not fit in an Int
  (-9223372036854775808 to 9223372036854775807)`; NaN and the infinities too.
  These are the only builtins that turn a Float into an `Int`.

## A name means its nearest declaration

- **A local named like an effect operation.** In compiled code a parameter or
  local binding named `ask` or `say` (the `Console` operations) or like any
  operation of a declared effect was taken as the operation: the function
  gained a hidden effect parameter and the generated Rust did not compile. The
  interpreter was right. Effect inference and code generation now follow the
  scopes of parameters, bindings, patterns and closure parameters.
- **An imported function named like a builtin.** A function named `first` or
  `last` in an imported file was mistaken for the builtin in generated Rust
  (an authored one already shadowed it). An imported function now shadows a
  builtin exactly as an authored one does, as in the interpreter.
- **A parameter called as a function.** `> g(f: Int) -> Int { f(f) }` passed
  `runa check --frontend` when a function or rule `f` existed; the interpreter
  then called the rule, or failed, and the generated Rust did not compile. A
  parameter, local binding or rule-scope field whose value is not a function
  is the nearest binder of its name, so calling it is a check error: ``value
  `f` is not callable: here `f` is a parameter, local binding or rule-scope
  field of type `Int`, which hides the function or rule `f` ``. This includes
  `income()` inside `# Case(income: Int) { … }` when a function `income`
  exists, which before called the function. A scalar top-level binding of a
  function's name (`= tax = tax(case)`) still leaves calls to the function.
- **Two top-level bindings of one name.** `= rate = 25` and later
  `= rate = 30` in one file or module were accepted, and the later value
  replaced the earlier one unseen. A second binding that does not read the
  name is a check error naming both lines. An update that reads it
  (`= scores = map_insert(scores, "fire", 1)`) stays a rebinding, and a body
  may still bind a local name again.
- **A rule and a function of one name.** `| tax(...)` beside `> tax(...)` was
  caught only when rustc rejected the generated code. It is a check error
  naming the line of each.
- **A bare `print(...)` in a function body.** IO is an effect, written
  `@ print(...)`; at top level the parser already said so. In a body a bare
  `print(...)` passed the checker and ran in the interpreter, but generated
  Rust that did not compile. It is now a check error in both modes: ``In
  Futuruna, IO is an effect: write `@ print(...)`, not a bare `print(...)`
  call``.

## An imported file's calls mean its own functions

- **The bug.** A function declared in the root file replaced an imported
  file's function of the same name everywhere, also in the imported file's
  own calls. With `a.runa` declaring
  `> isin_ok(s: String) -> Bool { length(s) == 12 }` and
  `> uses_check(s: String) -> Bool { isin_ok(s) }`, a `main.runa` that imports
  `a.runa` and declares its own `> isin_ok(s: String) -> Bool { True }`
  printed `true` for `uses_check("short")`, in the interpreter, in compiled
  code and in `runa call`, and the checker typed `a.runa`'s body against
  `main.runa`'s `isin_ok`. What a law module computed depended on the file
  that imported it. The 0.4.1 reference described this as intended: imported
  initializers and later calls used "that same final function and rule
  context".
- **The decision: an importing file may still declare the name.** A file may
  declare a function that a file it imports declares too. The reference has
  allowed it since plain imports were introduced ("local functions override
  imported functions"), the import tests rely on it, and a model must be able
  to name its own helper without knowing every name a law module declares.
  What changes is whose calls each declaration serves: a name in a file means
  what that file's own scope declares, its own function or else the one its
  plain imports provide (a later import's over an earlier one's), never a
  function of a file that imports it. `uses_check("short")` is now `false`,
  while `main.runa`'s own `isin_ok("short")` stays `true`. This holds in the
  checker, which types each body against its own file's declarations, in the
  interpreter, in `runa call` and WebAssembly, in compiled code and in
  `runa verify`; along a chain of imports; and for two imports that declare
  the same name, each of which keeps its own (the importing file sees the
  later import's, as before).
- **A name only an importing file declares.** For the same reason a call in
  an imported file that names no function of that file or of its imports,
  while a file importing it declares one, is now a check error located in the
  imported file: `` `hook` (line 3) names no function of this file or of the
  files it imports, but line 9 of the file being checked declares a function
  `hook` and imports this file ``. It called the importing file's function;
  a builtin of that name (`first`) was replaced in the imported file the same
  way.
- **A rule and a function in two files.** A rule family spans plain imports:
  an importing file's `| tax(...)` clause joins the imported family. So
  `| tax(...)` in one file and `> tax(...)` in another that one file's scope
  reaches are the clash one file already reports, and the check error names
  the line of each: `` `tax` is declared both as a rule (line 3 of
  rules.runa) and as a function (line 9) ``. The generated Rust did not
  compile ("defined multiple times"), and the interpreter called the function
  from the rule's callers.
- **How.** Two functions of one name that meet in a merged program are told
  apart: each one except the one the root file sees gets an internal name in
  its file and in every file that reaches it, and `Lib.fee` of a qualified
  import of such a file is rewritten alike. Programs without such a pair are
  not rewritten. The internal name never reaches the reader: diagnostics,
  runtime errors, a shown function value, calculation explanations and
  `runa verify`'s SMT-LIB script name the function as written, with its file
  (`` `isin_ok` in a.runa ``). A file's identity stays what it writes:
  content hashes and an `@ import #hash` selection read the written
  declarations, so a module has one identity whatever path or importer
  reaches it, and `? explore` resolves names as written (a helper two files
  declare is still refused there, as before).

## Units and `concat`

- **A declared binding with a number in one branch.**
  `= s: Micro = if c { 0 } else { amount }` and
  `= g: List(Micro) = if c { [0] } else { amounts }` were rejected ("binding
  expects `Micro` but expression has `Int`"), while the same expression as a
  function's result was accepted. A declared binding now checks each branch
  against its type, as a function's result does, so the number takes the
  binding's unit; a branch of another type is still an error.
- **`concat` of two strings.** `concat("a", "b")` ran in the interpreter but
  generated Rust that did not compile. Compiled code now joins the strings.
- **`concat` of plain numbers with a list of unknown type.** In a program that
  declares units, `concat([0], xs)` with `xs` of unknown type (an untyped
  parameter) had no type, so `head(concat([0], xs))` was accepted where a
  `String` was expected and the generated Rust failed. `[0]` could be a list
  of any unit, so no type can be given to it soundly. It is now an error that
  asks for the type: declare the type of `xs`, or write the numbers in their
  unit (`[Micro(0)]`). In a program without units it stays a `List(Int)`.

## Compatibility

### Models

- A program with two top-level bindings of one name where the second does
  not read the first, a rule and a function of one name, or a call of a
  parameter or local value of a non-function type now fails `runa check`. The
  first two were accepted and silently used one of the declarations; the third
  failed at runtime or in generated Rust.
- In a program that declares units, `concat` of a list of plain numbers with
  an argument of unknown type fails `runa check`.
- A function body that calls `print(...)` without `@` fails `runa check`;
  write `@ print(...)`.
- A program that relied on `round` or `floor` saturating a Float outside the
  `Int` range now stops with a runtime error.
- A program in which an imported file's own calls relied on the importing
  file's function of the same name now computes with the imported file's
  function. An imported file that calls a function only the importing file
  declares (or a builtin the importing file redeclares), and a rule and a
  function of one name in two files of one file's scope, fail `runa check`.
