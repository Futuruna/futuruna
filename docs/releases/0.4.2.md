# Futuruna 0.4.2

Futuruna 0.4.2 fixes one way a program could give a wrong answer without an
error, and nine places where a reader or writer could not rely on what they
read. `round(pow(10.0, 300.0))` returned `9223372036854775807`: a Float
outside the `Int` range became the largest `Int`. It is now an error that names
the value. A name now means what its nearest declaration says, in the checker,
the interpreter and compiled code alike: a local named `ask`, an imported
function named `first`, a parameter called as a function, two top-level
bindings of one name, and a rule and a function of one name. A bare
`print(...)` in a function body is an error that asks for `@ print(...)`, as
at top level.

0.4.2 rejects programs that 0.4.1 accepted; see
[Compatibility](#compatibility).

## `round` and `floor` never saturate

- **The bug.** `round` and `floor` of a Float outside the `Int` range gave the
  nearest `Int` (`9223372036854775807` for `round(pow(10.0, 300.0))`), and of
  NaN gave `0`, in the interpreter, in the interpreter compiled to WebAssembly
  and in compiled code. No error was reported.
- **The fix.** Both stop with a runtime error that names the value, in every
  mode with the same text: `round: 1e300 does not fit in an Int
  (-9223372036854775808 to 9223372036854775807)`; NaN and the infinities too.
  These are the only builtins that turn a Float into an `Int`.

## A name means its nearest declaration

- **A local named like an effect operation.** In compiled code a parameter or
  local binding named `ask` or `say` (the `Console` operations) or like any
  operation of a declared effect was taken as the operation: the function
  gained a hidden effect parameter and the generated Rust did not compile. The
  interpreter was right. Effect inference and code generation now follow the
  scopes of parameters, bindings, patterns and closure parameters.
- **An imported function named like a builtin.** A function named `first` or
  `last` in an imported file was mistaken for the builtin in generated Rust
  (an authored one already shadowed it). An imported function now shadows a
  builtin exactly as an authored one does, as in the interpreter.
- **A parameter called as a function.** `> g(f: Int) -> Int { f(f) }` passed
  `runa check --frontend` when a function or rule `f` existed; the interpreter
  then called the rule, or failed, and the generated Rust did not compile. A
  parameter or local binding whose value is not a function is the nearest
  binder of its name, so calling it is a check error: ``value `f` is not
  callable: here `f` is a parameter or local binding of type `Int`, which hides
  the function or rule `f` ``. A scalar top-level binding of a function's name
  (`= tax = tax(case)`) still leaves calls to the function.
- **Two top-level bindings of one name.** `= rate = 25` and later
  `= rate = 30` in one file or module were accepted, and the later value
  replaced the earlier one unseen. A second binding that does not read the
  name is a check error naming both lines. An update that reads it
  (`= scores = map_insert(scores, "fire", 1)`) stays a rebinding, and a body
  may still bind a local name again.
- **A rule and a function of one name.** `| tax(...)` beside `> tax(...)` was
  caught only when rustc rejected the generated code. It is a check error
  naming the line of each.
- **A bare `print(...)` in a function body.** IO is an effect, written
  `@ print(...)`; at top level the parser already said so. In a body a bare
  `print(...)` passed the checker and ran in the interpreter, but generated
  Rust that did not compile. It is now a check error in both modes: ``In
  Futuruna, IO is an effect: write `@ print(...)`, not a bare `print(...)`
  call``.

## Units and `concat`

- **A declared binding with a number in one branch.**
  `= s: Micro = if c { 0 } else { amount }` and
  `= g: List(Micro) = if c { [0] } else { amounts }` were rejected ("binding
  expects `Micro` but expression has `Int`"), while the same expression as a
  function's result was accepted. A declared binding now checks each branch
  against its type, as a function's result does, so the number takes the
  binding's unit; a branch of another type is still an error.
- **`concat` of two strings.** `concat("a", "b")` ran in the interpreter but
  generated Rust that did not compile. Compiled code now joins the strings.
- **`concat` of plain numbers with a list of unknown type.** In a program that
  declares units, `concat([0], xs)` with `xs` of unknown type (an untyped
  parameter) had no type, so `head(concat([0], xs))` was accepted where a
  `String` was expected and the generated Rust failed. `[0]` could be a list
  of any unit, so no type can be given to it soundly. It is now an error that
  asks for the type: declare the type of `xs`, or write the numbers in their
  unit (`[Micro(0)]`). In a program without units it stays a `List(Int)`.

## Compatibility

### Models

- A program with two top-level bindings of one name where the second does
  not read the first, a rule and a function of one name, or a call of a
  parameter or local value of a non-function type now fails `runa check`. The
  first two were accepted and silently used one of the declarations; the third
  failed at runtime or in generated Rust.
- In a program that declares units, `concat` of a list of plain numbers with
  an argument of unknown type fails `runa check`.
- A function body that calls `print(...)` without `@` fails `runa check`;
  write `@ print(...)`.
- A program that relied on `round` or `floor` saturating a Float outside the
  `Int` range now stops with a runtime error.
