# Futuruna 0.4.1

Futuruna 0.4.1 fixes two ways a program could give a wrong answer without an
error. A Rust program that ran a checked model through `Interpreter` after
checking a second model on the same thread could read the second model's
constructor names, and so could read a closed account as open. And
`runa check` accepted `head(concat([0], amounts))` where a `String` was
expected, because `concat` with a list of plain numbers had no type.

0.4.1 changes the Rust library's `Interpreter` constructors; see
[Compatibility](#compatibility). Models, calculation JSON and contracts are
unchanged.

## An interpreter runs with its own program's names

- **The bug.** Since 0.4.0 two sum types may share a constructor name, and a
  checked program gives the second one an internal name and reads its imports
  as elaboration rewrote them (see
  [Constructor names scoped to their type](0.4.0.md#constructor-names-scoped-to-their-type-experimental)).
  `runa`, prepared calculations and the WebAssembly engine run each program
  with its own names. An `Interpreter` made with `Interpreter::new()` did not:
  it read the names of whichever program its thread checked last. A program
  run after another was checked read its imports as written while its own
  statements used the internal names: a `match` found no arm for a closed
  account, or took a wildcard arm and answered "open" without an error.
- **The fix.** An interpreter now says whose names it runs with, and makes
  them current on its thread whenever it evaluates:
  `Interpreter::for_checked(&artifacts)` for a checked program (it also
  installs the program's rule dispatch metadata), and
  `Interpreter::unchecked()` for statements no check elaborated, which read
  no program's names. Two checked programs run alternately on one thread
  each give their own results; a test runs them through the public API.
- **Displaying values.** `Interpreter::display_value(&value)` writes a value
  with its program's declared constructor names. Formatting a `Value`
  directly reads the names current on the thread.

## `concat`, lists and branches keep their element type

- **The bug.** `= w: String = head(concat([0], amounts))` with
  `amounts: List(Micro)` passed `runa check`: a list of plain numbers such as
  `[0]` beside a list of a unit gave `concat` no type, so neither `head` nor
  the binding was checked. The program failed only when its generated Rust
  was compiled. `tail`, `last`, `nth`, `reverse`, `take`, `skip` and `first`
  of such a `concat` had the same hole.
- **The fix.** `concat`'s result has the type both arguments share. A list of
  plain numbers takes the unit of the list beside it, so the example's
  `concat` is a `List(Micro)`, and the binding is an error ("binding expects
  `String` but expression has `Micro`"). An argument of unknown type takes the
  other's; `concat([0], xs)` with `xs` unknown is a `List(Int)` in a program
  that declares no unit.
- **Two different lists are an error.** `concat([0], ["a"])` and
  `concat("a", [1])` are rejected: `concat` joins two lists of one element
  type, or two strings. A list of plain numbers joins a list of any unit.
- **`first` on a list** has the list's element type, like `head`. It had no
  type, so `first(amounts)` was accepted where a `String` was expected.
- **Lists and branches with plain numbers.** With `amount: Micro`, the list
  `[0, amount]` and `if c { [0] } else { amounts }` had no type either; they
  are lists of `Micro` now, as `if c { 0 } else { amount }` already was a
  `Micro`.

## Compatibility

### Rust library

- `Interpreter::new()` is no longer public. Use
  `Interpreter::for_checked(&artifacts)` to run `artifacts.program()`, or
  `Interpreter::unchecked()` for statements no check elaborated. A host that
  kept only a program's `TypeCheckArtifacts::constructor_elaboration` uses
  `Interpreter::for_constructor_elaboration(elaboration)`.
  `for_checked` installs the rule dispatch metadata, so a separate
  `install_rule_dispatch_metadata(&artifacts)` call can go.

### Models

- A model that joins two lists of different element types with `concat`, or
  returns, binds or passes `concat`'s result as another type, now fails
  `runa check`. Such a program failed at runtime or in generated Rust before.
