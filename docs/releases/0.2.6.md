# Futuruna 0.2.6

Futuruna 0.2.6 fixes three cases in which the interpreter and compiled code
gave different results, and a set of programs the interpreter runs that
failed to compile to native code. They were found by checking every builtin
and type in every syntactic position in both execution modes, by compiling a
real service's work in progress, by testing each claim of the 0.2.3 release
notes, and by reading the failing scheduled CI runs.

## Interpreter and compiled code agree

- **`Pair` values from a qualified import.** A `Pair` built inside
  `@ import L from ./lib` was a different value in the interpreter: it showed
  as `Pair(1, a)` instead of `(1, a)`, was not equal to the same `Pair` built
  by the importing file, and a `Set` kept both. Compiled code treated them as
  the same tuple. The constructors of the prelude types (`Pair`, `Option`,
  `Result`, `ProgramReference`) now mean the same value in every module that
  does not declare its own.
- **`Pair` and tuples are one value.** `Pair(1, "b") == (1, "b")` was `false`
  in the interpreter and `true` in compiled code, and a `Set` or `Map` kept a
  `Pair` and the equal tuple apart. They now compare, order and hash alike.
- **A failed HTTP connection reads the same.** When `http_get` or `http_post`
  cannot reach the server, both modes return `request to URL failed: cannot
  connect` (or `cannot resolve host`). The interpreter used to pass on curl's
  message and compiled code its HTTP library's, so `examples/tax-client.runa`
  failed the daily differential run.

## Native compilation

- **A record field passed to a rule.** `similar(k.facts, ours)` inside a
  closure that later returns `k` moved the field out of `k`, and rustc
  rejected the program ("borrow of partially moved value"). A field passed
  by value is copied when its record is used again. This was present since
  at least 0.2.3.
- **Lambdas passed to generic functions.** A lambda argument to a function
  such as `> group_by_key(items: List(a), key: a -> String)` gets the
  parameter type from the function's signature, with `a` taken from the other
  arguments. Before, compiled code guessed a type from the lambda's body
  (`i64`, `(i64, i64)`, or the first record with a field of that name) and
  rustc rejected it. The same change compiles a closure passed for a
  tuple-typed parameter, such as `k(|p| p)` for `((Int, Int)) -> (Int, Int)`,
  a known issue of 0.2.5.
- **`sort_by` with a function parameter.** `sort_by(items, key)` where `key`
  is a parameter of function type compiles.
- **Rules and functions ending in collection builtins.** A result coming from
  `map`, `flat_map`, `map_from`, `map_entries`, or `map_get`/`map_keys`/
  `map_values` over `map_from(...)` is typed; such rules were skipped with
  "cannot infer every return clause".
- **Generic constructors as rule results and parameters.** `| pair_of(n: Int)
  -> Pair(n, "a")`, a rule returning `Box(item = n)` for `# Box(a) = Box(item:
  a)`, and a rule parameter `b: Box(Int)` compile; the Rust signature named
  `Pair` or `Box` without type arguments. A field of an applied generic type,
  such as `b.item` for `b: Box(Int)`, has the substituted type.
- **`pair`, `triple`, `show_int` and `show_float`** run in compiled code; they
  existed only in the interpreter.
- **A declared lambda parameter type is kept** in `map`, `filter` and
  `partition`, so `map([[], [1]], |xs: List(Int)| xs)` compiles.
- **A record field that holds a function** (`# Counter(step: Int -> Int)`)
  is reported by `runa check`, `run` and `build` at the declaration: compiled
  code cannot store a function in a record. It used to fail inside rustc. The
  interpreter still runs such programs.

## Type checking

- **A closure's declared parameter types are checked at its calls.**
  `= scale = |x: Float| x * 2.0` followed by `scale(3)` is a type error, as it
  is for a declared function; it used to run interpreted and fail natively.
- **Float keys.** `map_from([(1.5, "a")])` and a key or set element whose
  record contains a `Float`, such as `Price(amount = 1.0)`, are the documented
  check error. The tuple form and records slipped past the check.
- **A builtin's two-element tuple result is a `Pair`.** A function declared
  `-> Pair(Int, String)` may end in `head(zip(...))`, and a `Pair` parameter
  accepts `head(map_entries(m))`. Since 0.2.5 typed the results of `zip` and
  `enumerate`, such calls were rejected as `Tuple(Int, String)`.

## Documentation

- The standard library reference no longer says that `sort` orders numbers as
  text; `sort` uses value order.

## Installation

Use the checksummed binaries on the
